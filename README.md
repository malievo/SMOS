# SMOS — Split Management Operating Shell

Голосовая модульная среда для управления компьютером через речь. Не «ещё один
ассистент», а попытка собрать голосовое взаимодействие как **маленькое ядро +
много независимых заменяемых модулей** — так, чтобы это работало и на ПК, и на
Raspberry Pi, и на сервере без экрана.

> **Статус:** в активной разработке. Сквозной путь «голос → распознавание →
> классификация → цель → выполнение → озвученный ответ» работает, за ним
> стоят настоящие модули (дата/время, показатели машины, калькулятор,
> заметки, журнал). Многое ещё не построено — см. [Состояние](#состояние).

## Идея

- **Не монолит.** Одно минимальное ядро + модули, которые ничего не знают о
  внутренностях друг друга и общаются только через ядро.
- **Прямая связь там, где нет выбора; координатор — только там, где есть
  реальная развилка.** Логи и линейные пайплайны общаются напрямую. Ядро
  нужно там, где приходится динамически решать, *какой модуль* берёт задачу
  и в каком порядке.
- **Без LLM в горячем пути принятия решений.** Планировщик — классический
  GOAP-поиск по графу возможностей модулей, не нейросеть: быстро, локально,
  годится для слабого железа. Облачная LLM (GigaChat) используется только как
  временные «леса» на этапе bootstrap (классификация фразы и разбор её в
  цель), с прицелом на дистилляцию в локальную модель.
- **Модуль = папка + манифест.** Новый модуль добавляется без единой правки
  в ядре. Личные данные модуля живут отдельно от его кода и переживают
  переустановку.

## Архитектура

```
                   ┌─────────── FWL — первый рабочий цикл ─────────────┐
  микрофон ──────► │  wake.py     wake-word (openWakeWord, локально)    │
                   │              + запись фразы целиком                │
                   │  req.py      речь → текст (Google STT)            │
                   │  classifier  «команда» / «разговор»               │
                   │              (GigaChat → дистилляция в локальную)  │
                   └───────────────────────┬──────────────────────────┘
                                           │  label == "command"
                   ┌─────────── SWL — второй рабочий цикл ─────────────┐
                   │  swl.py      фраза → { goal, params }             │
                   │              (GigaChat на bootstrap-этапе)        │
                   └───────────────────────┬──────────────────────────┘
                                           │  goal.json → system/core/goals/
                   ┌─────────────── CORE — демон ядра ─────────────────┐
                   │  module_init  скан модулей → граф needs/produces  │
                   │  planner      GOAP backward-chaining: achieve()   │
                   │  task_runner  поток на задачу, статус в файле     │
                   └───────────────────────┬──────────────────────────┘
                       subprocess:  main.py <command> '<json-params>'
                       env:         SMOS_MODULE_DATA=user/module_data/<name>
                            ┌──────────────┴───────────────┐
                            ▼                               ▼
                     system/modules/*                user/modules/*
                (calc, datetime, sysinfo,           (личные модули
                 notes, journal + тестовые)          пользователя)
                            │
                   ┌────────┴──────── выходная сторона ────────────────┐
                   │  outputstructurizer  результат задачи → фраза     │
                   │                      (готовый шаблон / GigaChat)  │
                   │  audio (v1)          фраза → Google TTS → произнесено │
                   └──────────────────────────────────────────────────┘

  Все процессы → logs/listener  (UDP :47110, fire-and-forget)
                 → logs/raw/<module>/events.jsonl

  smos.py — единая точка входа: preflight + запуск/остановка всех процессов
```

### Как планировщик строит путь

Цель `journal_written`. Модулю журнала нужны `current_datetime` и
`system_stats` — их в состоянии задачи нет. Планировщик находит в графе
`mod_datetime` и `mod_sysinfo` (оба ничего не требуют на входе), вызывает
их, собирает результаты и передаёт `mod_journal`. Рёбер
`journal → datetime, sysinfo` нигде не прописано — планировщик выводит их
из `needs`/`produces`.

То же с погодой: `weather` требует `city`; если города нет — планировщик
находит модуль, который его производит; если город уже был в фразе
(«погода в Питере») — этот шаг просто пропускается.

## Состояние

| Часть | Статус |
|---|---|
| FWL: wake word + запись + STT (`system/fwl/rvs/`) | ✅ работает от микрофона |
| FWL: классификатор команда/разговор (`system/fwl/classifier/`) | ✅ работает; реализован цикл дистилляции `bootstrap → shadow → validating → offline` |
| SWL: фраза → структурированная цель (`system/swl/`) | ✅ bootstrap-версия (GigaChat) проверена вживую |
| CORE: реестр модулей + GOAP-планировщик + task runner | ✅ проверено end-to-end, включая многошаговые цепочки |
| Модули: 5 реальных (`mod_*`) + 5 тестовых фикстур | ✅ |
| Личные папки данных модулей (`user/module_data/<name>/`) | ✅ |
| ВЫХОД: `outputstructurizer` (результат задачи → фраза, 3 слоя: шаблон → GigaChat → сырой fallback) | ✅ v1, проверено end-to-end |
| ВЫХОД: `system/audio/` v1 (фраза → озвучка; движки: Google TTS `gtts` по умолчанию / `spd-say`) | ✅ v1 |
| Логирование (`logs/`) | ✅ работает |
| Единый запуск/остановка (`smos.py`) | ✅ |
| Аналитический слой поверх сырых логов | ⛔ не построен |
| Ветка «разговор» (`label == "chat"`) | ⛔ не обрабатывается |
| Полный аудио-демон (приоритетная очередь, музыка, приглушение) | ⛔ пока только v1 «сказать текст» |
| Поле `speech` от модулей (точная дословная формулировка) | ⛔ не делали в v1 выхода |
| Дистилляция формулировщика `outputstructurizer` в локальную модель | ⛔ датасет копится, цикл — потом |
| Дистилляция SWL в локальную модель | ⛔ план есть, пока только накопление датасета |
| Определение зависшего модуля по heartbeat | ⛔ пока жёсткий таймаут 5 c |
| Долгая память / персона, проактивность (напоминания, ambient-звук) | ⛔ не начаты |
| Механизм обновления системы | ⛔ проектируется |

Нужно ли SMOS «настоящее» центральное ядро в том виде, как задумывалось
изначально — **открытый вопрос**. Текущее ядро появилось только там, где
реально понадобилась координация (планирование многошаговых команд), а не
потому что «так было в плане».

## Модули

Реальные (работают с настоящими данными, имя в манифесте — `mod_<name>`):

| Модуль | Действие | `needs` → `produces` | Что делает |
|---|---|---|---|
| `mod_datetime` | `get_datetime` | → `current_datetime` | текущие дата, время, день недели, таймзона |
| `mod_sysinfo` | `get_system_stats` | → `system_stats` | загрузка, память, диск, аптайм, ядра (из `/proc`, без зависимостей) |
| `mod_calc` | `evaluate` | `expression` → `calc_result` | арифметика: разбор через `ast`, вычисление обходом дерева, без `eval` |
| `mod_notes` | `add_note` / `list_notes` | `note_text` → `note_saved` / → `notes_list` | заметки в личной папке данных модуля |
| `mod_journal` | `write_snapshot` | `current_datetime`, `system_stats` → `journal_written` | снимок состояния в журнал; тянет два модуля выше — пример многошагового графа |

Тестовые фикстуры (`clock`, `echo`, `greeting`, `location`, `weather`) —
фиктивные данные, нужны только для проверки сканера и планировщика.

## Структура репозитория

```
smos.py         единая точка входа: preflight, запуск и остановка всех процессов
smos.root       пустой файл-маркер корня проекта
system/
  fwl/          системные процессы первого цикла
    rvs/          wake.py, req.py — микрофон → текст
    classifier/   команда vs разговор + цикл дистилляции
  swl/          фраза → структурированная цель
  core/         демон ядра
    module_init/   скан модулей, валидация манифестов, граф needs/produces
    planner/       GOAP-разрешение цели (achieve)
    task_runner/   поток на задачу, статус в tasks/<id>/state.json
  outputstructurizer/  результат задачи → человеческая фраза
                       (шаблон phrases.json / GigaChat-формулировщик)
  audio/        озвучка, v1: заявки в tasks/ → Google TTS (gtts) / spd-say
  modules/      модули, поставляемые с репозиторием
  launcher/     рантайм-состояние smos.py (system/launcher/run/)
logs/
  listener/     демон-приёмник логов (UDP :47110)
  PROTOCOL.md   как модулю слать события
user/           данные пользователя (в .gitignore, кроме configs/)
  configs/        *.json — настройки процессов (значения по умолчанию — в коде)
  modules/        личные модули
  module_data/    <name>/ — личная папка данных каждого модуля
  .env            GIGACHAT_CREDENTIALS

```

## Запуск

Требуется Python 3.12.

```bash
python -m venv .venv && source .venv/bin/activate
pip install openwakeword pyaudio SpeechRecognition gigachat python-dotenv \
            scikit-learn sentence-transformers joblib numpy scipy gtts
```

Озвучка ответа (`system/audio/`) по умолчанию идёт через Google TTS
(`gtts`, онлайн) + MP3-плеер — поставь `gst-play-1.0` (пакет
`gstreamer1.0-tools`), либо `mpg123`/`ffplay` и укажи его в
`user/configs/audio.json` → `tts.gtts.player`. Оффлайн-альтернатива —
`tts.engine: "spd-say"` (speech-dispatcher).

Ключ GigaChat (нужен для bootstrap-этапов классификатора и SWL) — в
`user/.env`:

```
GIGACHAT_CREDENTIALS=<ваш ключ>
```

Всё поднимается одной командой (`smos.py` сначала делает preflight —
проверяет venv, пакеты, конфиги, ключ):

```bash
.venv/bin/python smos.py            # preflight + запуск всех процессов, общий вывод; Ctrl+C гасит всех
.venv/bin/python smos.py status     # кто жив, pid, uptime, режим классификатора
.venv/bin/python smos.py stop       # погасить всё, что запускал launcher (даже из другой консоли)
```

Полезные флаги: `--debugview` (каждый процесс в своей панели `tmux`),
`--only swl,core`, `--skip wake,req`, `--restart` (поднимать упавший
процесс заново с backoff).

Проверить часть пайплайна без микрофона:

```bash
.venv/bin/python system/swl/swl.py "запиши снимок системы в журнал"
# фраза → GigaChat → цель → очередь ядра → планировщик → mod_datetime + mod_sysinfo → mod_journal
# → outputstructurizer (фраза) → system/audio/ (озвучка), если запущены
```

Только выходную сторону (без SWL и микрофона) — положить файл-результат
прямо в очередь `outputstructurizer`:

```bash
echo '{"task_id":"manual_1","goal":"calc_result","status":"done","result":{"expression":"2+2","value":4},"state":{},"source_text":"посчитай"}' \
  > system/outputstructurizer/queue/manual_1.json
# outputstructurizer подхватит (если запущен ПОСЛЕ появления файла) → фраза → system/audio/tasks/
```

Настройки — в `user/configs/*.json`. Любой файл можно удалить: процесс
возьмёт значения по умолчанию из своего `config.py` (там же — комментарии к
каждому полю).

## Свой модуль

Модуль — папка в `system/modules/` или `user/modules/` с `manifest.json` и
точкой входа:

```json
{
  "name": "mod_weather",
  "description": "Погода по городу",
  "entrypoint": {"command": ["python3", "main.py"]},
  "actions": [
    {"command": "get_weather", "description": "Текущая погода",
     "needs": ["city"], "produces": ["weather_forecast"], "cost": 1}
  ]
}
```

Ядро вызывает модуль как отдельный процесс:
`main.py <command> '<json-параметры>'`. Модуль печатает **один** JSON-объект
в stdout и завершается:

```python
# {"status": "ok",      "data": {"weather_forecast": {...}}}   успех
# {"status": "missing", "missing": ["city"]}                    не хватает параметра — планировщик добудет его сам
# {"status": "error",   "error": "..."}                         ошибка
```

- `needs` / `produces` — узлы графа, по которому планировщик ищет путь к
  цели. Модули сканируются **при старте** ядра (без hot-reload — новый
  модуль виден после перезапуска).
- Личные данные модуля: ядро на каждом вызове передаёт переменную окружения
  `SMOS_MODULE_DATA` — абсолютный путь к папке `user/module_data/<name>/`.
  Что и как хранить внутри (JSON, SQLite, plain text) — дело модуля. Папка
  отдельно от кода и переживает удаление/переустановку модуля; ключ к ней —
  поле `name` из манифеста.
- Логирование (по желанию, но рекомендуется): один UDP-пакет с JSON на
  `127.0.0.1:47110`, формат — в [`logs/PROTOCOL.md`](logs/PROTOCOL.md).
  Клиент — ~15 строк без зависимостей, копируется в папку модуля.

## О проекте

Личный проект. Идея записана «на бумаге» несколько лет назад, когда
технических знаний на нормальное ТЗ не хватало; сейчас — попытка собрать из
тех заметок что-то работающее и по ходу разобраться, что вообще технически
осмысленно. Дизайн-решения фиксируются в файлах `*_design.md` рядом с кодом,
который они описывают — не как финальная спецификация, а как журнал того,
почему сделано именно так.
