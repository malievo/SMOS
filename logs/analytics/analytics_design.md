# Аналитический слой логов — дизайн

**Статус: v1 построен 2026-09-08.** Ветка `dev/analytics`. Первый
потребитель сырых логов (`logs/raw/*/events.jsonl`) кроме глаз.

Родственное: [`logs/PROTOCOL.md`](../PROTOCOL.md) (формат событий +
`trace_id`), [`logs/listener/listener.py`](../listener/listener.py)
(кто пишет сырьё), заметка проекта про логирование.

---

## Зачем

Логи копились с самого начала, но сверх «дозаписать в файл» с ними
ничего не делалось — а исходная цель была именно анализ. Слой отвечает
на четыре вопроса, на которые раньше отвечали догадками:

1. **Где система теряет команды?** — воронка по стадиям.
2. **Что тормозит?** — разбор задержки микрофон→ответ по участкам.
3. **Что ломается / ведёт себя странно?** — аномалии и здоровье.
4. **Что пользователь реально просит?** — поведение.

## Граница

Слой **только читает** `logs/raw/*/events.jsonl`. С кодом модулей не
связан вообще — это и был смысл архитектуры логов (модуль зависит от
тонкого протокола, не от системы логов). Добавить/поменять анализ можно,
не трогая ни один модуль. Единственное, что слой сам делает в системе, —
в режиме `watch` шлёт СВОИ события обратно в ту же шину
(`module="analytics"`), как любой другой модуль.

## Предпосылка: `trace_id`

Чтобы «сшить» события разных модулей в историю одной реплики, нужен
сквозной id. Его не было — добавлен отдельно (см.
[`logs/PROTOCOL.md`](../PROTOCOL.md)): рождается в `wake.py` при начале
записи, едет `rvs → classifier → swl → core/task_runner → planner →
outputstructurizer → cnps`, каждая стадия кладёт его в то, что передаёт
дальше (файл-хендовер / заявка), и в свои `send_log`. Конец истории —
`cnps` `delivery`.

События старше этого изменения `trace_id` не имеют: **воронка и
задержка** считаются только по репликам с `trace_id`; **аномалии и
поведение** — по всем событиям окна.

## Файлы

| Файл | Что |
|---|---|
| `pipeline.py` | ЕДИНСТВЕННОЕ место, где зашита форма воронки: список стадий `STAGES` + для каждой `(module, message)`, которые её отмечают достигнутой (`reached`) или проваленной (`failed` + причина). Меняется цепочка — правится здесь, отчёты подстраиваются. |
| `analytics.py` | сам инструмент: загрузка событий за окно, группировка по `trace_id`, `TraceView` (докуда дошла реплика, где встала, label/goal/outcome), функции `funnel` / `latency` / `anomalies` / `behavior`, печать + подкоманды. |
| `store.py` | постоянное хранилище истории по каждой команде: `watch` отдаёт сюда собранную запись реплики, она пишется одним файлом `traces/<дата>/<trace_id>.json` + строкой в `traces/index.jsonl` при закрытии. Только запись в свою папку. |
| `config.py` | как у `listener/config.py`: `DEFAULTS` + `user/configs/analytics.json`, рекурсивное слияние, не падает. |
| `log_client.py` | копия эталонного клиента, `module="analytics"` — нужен только `watch`. |

## Подкоманды

```
analytics.py report [--since ISO | --last 24h] [--json]
analytics.py trace <trace_id> [--last 7d]
analytics.py traces [--last 7d] [-n 20] [--raw]
analytics.py watch
```

- **report** — полный отчёт за окно. `--json` — машиночитаемо (под сайт /
  дальнейшую обработку). Считается всегда по сырым логам, хранилище ему
  не нужно.
- **trace** — таймлайн одной реплики: строка на событие, `Δt` от
  предыдущего, разбор задержки по участкам, ключевые поля `data`. Это
  ответ на исходную просьбу — «смотреть проход команды от микрофона до
  выполнения». Сначала смотрит в хранилище (мгновенно, если `watch` его
  писал), иначе собирает на лету из сырых логов за окно.
- **traces** — последние N реплик: докуда дошли, статус
  (`ok`/`partial`/`chat`/`silent-ok`/`failed`/`dropped`), цель, задержка.
  По умолчанию из `index.jsonl` (вся история, быстро); `--raw` — свежий
  разбор сырых логов за окно.
- **watch** — демон. Раз в `poll_interval_sec` перечитывает скользящее
  окно `report_window_min` и:
  - **пишет хранилище команд** (см. ниже) — собирает события каждой
    реплики по `trace_id` в один файл;
  - считает аномалии, шлёт новые обратно в шину (`anomaly_*`) +
    периодическую `window_summary`, печатает компактную строку. Повторно
    ту же аномалию не чаще ширины окна.

## Хранилище истории по командам (`store.py`)

Без `watch` события одной команды разбросаны по `logs/raw/<module>/…` и
собираются только по запросу (`trace <id>` сканирует всё заново).
`watch` с включённым `store` (по умолчанию) на каждом опросе:

- для каждой реплики в окне собирает `TraceView.to_record()` — id,
  начало/конец, докуда дошла, статус, `goal`/`label`/`outcome`, задержка
  по участкам, **полный список событий** — и перезаписывает
  `traces/<YYYY-MM-DD>/<trace_id>.json` (идемпотентно);
- когда реплика закрыта (`cnps delivery` **или** молчит дольше
  `idle_close_sec`) — один раз дописывает строку в `traces/index.jsonl`.

`watch_state.json` (gitignored) помнит, какие `trace_id` уже в индексе,
чтобы не дублировать при перезапуске. Папки-дни старше `keep_days`
`watch` подчищает на старте; `index.jsonl` не трогается (одна строка на
команду — растёт медленно; ротация — когда/если понадобится).

Даёт: посмотреть историю любой команды мгновенно и без сырых логов;
список всей истории (`traces`); материал для отчётов за длинный период,
когда сырьё уже проредят.

## Что считается

### Воронка
Стадии из `pipeline.py`, по порядку. Для каждой — сколько реплик
дошли **не меньше** этой стадии; между стадиями — сколько отвалилось и
почему (агрегированные причины из `failed`-событий). `label == "chat"`
на стадии `classified` — **легитимный выход** из воронки команд, считается
отдельно, не как потеря. `completion_silent` после `executed` — тоже не
потеря (ответ намеренно без озвучки, напр. `mod_playback`).

### Задержка
Для каждой реплики — `Δt` между соседними стадиями (по первому событию
стадии) + суммарная `heard→spoken`. Агрегат: p50 / p95 / max / n на
участок. **Разрешение `ts` — 1 секунда** (listener пишет
`timespec="seconds"`), поэтому доли секунды видны как 0 — участок
осмыслен только для ощутимо долгих (STT, GigaChat у SWL, синтез+озвучка).
Порог «медленно» на участок — `latency.slow_gap_sec`.

### Аномалии / здоровье
- ошибки (`ERROR`/`CRITICAL`) по модулям + темп в час (порог
  `error_spike_per_hour`);
- хлопанье перезапусками (`smos/all_system_started`, иначе
  `core/core_started`; НЕ каждый `*_started`, иначе один старт = пачка);
- доля неудачного STT (`speech_not_recognized` + `stt_request_error`);
- `cnps` `synth_fallback` — ушёл на запасной движок синтеза (прокси
  здоровья сети/пакетов);
- зависшие задачи: `task_started` без `task_done`/`task_failed` дольше
  `hang_timeout_sec`;
- отклонённые заявки (`goal_rejected` / `task_rejected` / `result_rejected`);
- залипший `mute.flag`: файл активен по формату, но не обновлялся дольше
  `mute_flag_stuck_sec` — CNPS мог упасть в середине озвучки, `wake.py`
  оглох. Единственная проверка, которая смотрит не в логи, а в живой
  файл (по пути от корня проекта).

### Поведение
частоты по `goal`; команда/чат; распределение по часам суток; фразы
`no_intent_match` дословно (кандидаты в новые модули); слой формулировки
ответа (`template`/`llm`/`fallback`); источник классификатора
(`llm_api`/`local` — прогресс дистилляции).

## Решения / что осознанно НЕ сделано

- **`trace_id` как отдельное поле верхнего уровня**, не внутри `data` —
  это сквозная метаданность вроде `ts`, а не полезная нагрузка события.
  `send_log(..., trace_id=None)` — 4-й необязательный параметр, старые
  копии `log_client.py` без него совместимы.
- **`report` пишет в stdout, не в файл.** Никакого накопления
  агрегатов/БД в v1. Каждый запуск читает сырьё заново. JSONL за годы —
  сотни КБ, читается мгновенно; когда перестанет — тогда и SQLite/кэш.
- **`watch` НЕ в `smos.py` PROCESSES.** Слой только наблюдает и
  докладывает, на поведение системы пока не влияет — включается вручную
  (`python3 logs/analytics/analytics.py watch`). Когда `watch` докажет,
  что его аномалии не шумят, — можно добавить `Proc("analytics", ...)`
  и повесить голосовые предупреждения через CNPS (`source:"watcher"`).
- **Обратная связь в поведение системы** (авто-таймауты модулей из
  распределения времён, приоры по частоте для планировщика,
  подложка под проактивность) — НЕ в v1. Сначала слой должен показать,
  что данным можно доверять. Подход тот же, что у классификатора:
  наблюдать → проверять → включать.
- **Разрешение `ts` не трогали.** Секундного хватает для участков,
  которые реально долгие. Если понадобится профилировать быстрые
  участки — отдельное изменение в listener (`timespec="milliseconds"`).
- **Модули-исполнители в трейс пока не попадают.** `planner` кладёт
  `SMOS_TRACE_ID` в окружение модуля и логирует свои ошибки вызова с
  `trace_id`, но `log_client.py` копии в модулях сигнатуру ещё не
  получили — чистое продолжение, когда понадобится видеть шаги внутри
  задачи.
