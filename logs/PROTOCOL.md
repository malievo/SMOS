# Протокол отправки логов SMOS

Как любому модулю SMOS отправлять события в систему логирования. Это
единственное, что нужно знать модулю — дальше (хранение, анализ) не
его забота.

## Куда отправлять

UDP-пакет с JSON на `127.0.0.1:47110` (актуальный адрес — в
[`user/configs/logs.json`](../user/configs/logs.json), если его меняли;
поставляемое значение по умолчанию — в `listener/config.py`, `DEFAULTS`).

Отправка **ничего не гарантирует и никого не блокирует**: если демон
логов сейчас не запущен — пакет просто теряется, отправитель не видит
ошибки и продолжает работать. Логирование не должно быть точкой отказа
модуля, который логирует.

## Что отправлять

```json
{"module": "rvs", "level": "INFO", "message": "wake_word_detected", "data": {"score": 0.87}, "trace_id": "20260908_120000_a1b2c3d4"}
```

| Поле       | Обязательно | Описание                                                                 |
|------------|-------------|-------------------------------------------------------------------------|
| `module`   | да          | имя модуля, латиницей, как в структуре проекта (`rvs`, ...)              |
| `level`    | да          | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL`                      |
| `message`  | да          | короткий машинно-читаемый код события, `snake_case` (не текст для людей) |
| `data`     | нет         | произвольные подробности — только JSON-совместимые типы                  |
| `trace_id` | нет         | сквозной идентификатор одной реплики пользователя (см. ниже)             |

Время (`ts`) **не указывается** — его проставляет демон в момент
приёма, поэтому не нужно ни знать формат, ни следить за часами.

### `trace_id` — путь одной реплики от микрофона до ответа

`trace_id` рождается в `wake.py` в момент начала записи фразы и едет по
всей цепочке: `rvs → classifier → swl → core/task_runner → planner →
outputstructurizer → cnps`. Каждая стадия читает его из того, что ей
пришло (файл-хендовер или заявка), и проставляет во всё, что производит
дальше, — и в свои лог-события. Так события разных модулей про одну и ту
же фразу можно «сшить» в единую историю: где реплика застряла, сколько
заняла каждая стадия. Читает эти истории `logs/analytics/`
(`analytics.py trace <trace_id>` / `report`).

Стадия вне этой цепочки (демон логов, апдейтер, разовый служебный клип)
`trace_id` просто не указывает — поле необязательное. Модуль-исполнитель,
запущенный ядром, получает `trace_id` своей задачи в переменной
окружения `SMOS_TRACE_ID` (может проставить его в свои логи, если хочет
попасть в ту же историю).

Осторожно с `data`: значения из ML/аудио-библиотек часто приходят как
`numpy.float32`/`numpy.int64` и подобные типы — они не сериализуются в
JSON напрямую, приводи к обычным `float`/`int` перед отправкой.

## Как отправлять (Python, без зависимостей)

```python
import json, socket

_sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)

def send_log(module: str, level: str, message: str, data: dict | None = None,
             trace_id: str | None = None) -> None:
    payload = {"module": module, "level": level, "message": message}
    if data:
        payload["data"] = data
    if trace_id:
        payload["trace_id"] = trace_id
    try:
        _sock.sendto(json.dumps(payload, ensure_ascii=False, default=str).encode("utf-8"), ("127.0.0.1", 47110))
    except (OSError, TypeError, ValueError):
        pass  # логирование не должно ронять модуль
```

`trace_id` — необязательный: модуль, который не участвует в разборе
реплики, его просто не передаёт (сигнатура остаётся совместимой со
старыми копиями `log_client.py` без этого параметра).

Библиотеку тащить не нужно — это весь код целиком, копируется в папку
своего модуля (готовый пример: [`system/fwl/rvs/log_client.py`](../system/fwl/rvs/log_client.py)).
Для не-Python модулей — то же самое: один UDP-пакет с JSON того же
формата, на том же адресе.

## Куда это попадает дальше

Демон ([`listener/listener.py`](listener/listener.py)) раскладывает
события по `logs/raw/<module>/events.jsonl` — по файлу на модуль,
дозапись. Это уже не забота отправителя.
