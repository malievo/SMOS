# outputstructurizer — дизайн

**Статус: v1 построена и проверена end-to-end 2026-08-28.** Промежуточный
этап выходной стороны SMOS: между ядром (выполнение задачи) и озвучкой.
Стоит рядом с `system/core/`, `system/swl/`, `system/audio/`.

Предыстория и общая картина выхода — `../audio/audio_design.md` (раздел
«v1: замыкание цикла») и `../audio/IDEA_responder_v2_chat_branch.md`.
Отдача результата ядром — `../core/core_design.md` (раздел «Отдача
результата дальше»).

## Зачем отдельный процесс

Ядро посчитало результат задачи (`system/core/tasks/<id>/state.json`,
`status: done`) — это структурные данные (`{"value": 22}`,
`{"time": "14:30:05", ...}`), а не фраза. Кто-то должен превратить их в
предложение, которое не стыдно произнести вслух. Это не работа ядра
(центрального NLG внутри ядра по дизайну нет), не работа модуля (модуль
знает свой результат, но не то, как SMOS разговаривает с пользователем),
и не работа аудио-демона (тот только владеет динамиком и проигрывает
готовое).

Форма — как у `swl.py` / `core.py`: системный процесс, поллит
папку-очередь, у общения всё файловое.

```
ядро/task_runner  ──► system/outputstructurizer/queue/   (файл на задачу)
                          │  outputstructurizer: result/error -> фраза
                          ▼
                    system/audio/tasks/                    (заявка на озвучку)
                          │  аудио-демон: text -> spd-say
                          ▼
                      произнесено
```

Вход — `queue/`, его уже наполняет ядро (`task_runner._emit_completion`
пишет туда компактный файл-результат: `task_id`, `goal`, `status`,
`result`, `error`, `state`, `source_text`, `ts`). Формат файла задаёт
ядро, не мы — правки в ядре под этот этап не понадобились.

## Три слоя формулировки

Решено с автором 2026-08-28 (уточнение слоёного fallback из
`audio_design.md`: **поле `speech` от модулей в эту версию не входит** —
модули не трогаем, planner/task_runner не трогаем).

Сверху вниз, `phrasing.render()`:

1. **Готовая фраза** — шаблон из `phrases.json` по goal-ключу (для
   `status == "error"` — ключ `_error`). Подстановка `str.format` по
   именам `result` / `state` / `source_text` / `goal` / `error`.
   Значение под ключ — строка или список строк (тогда случайный
   вариант, `phrasing.random_variants`). Оффлайн, мгновенно,
   предсказуемо. Для подтверждений команд («записал», «сейчас 14:30»,
   «получается 22») этого достаточно — и это **правильно**, а не
   компромисс: результаты структурны и однообразны.
   Шаблон ссылается на несуществующее поле → `template_render_failed` в
   лог, роняем на слой 2 (не падаем).

2. **Формулировщик (GigaChat)** — `phrase_provider.formulate()`. Когда
   готового шаблона нет. Системным промтом сообщается, что за команда
   выполнена (`goal`), как её произнёс пользователь (`source_text`) и
   каков результат модуля (`result` / `error`); модель возвращает одну
   короткую естественную фразу. **Отдельный тонкий файл** — как
   `swl/intent_provider.py` и `classifier/ai_provider.py`: единственное
   место, знающее про GigaChat, сигнатура `formulate(...)` наружу
   стабильна. Провайдера легко заменить (или увести формулировку в
   chat-ветку целиком, см. `IDEA_responder_v2_chat_branch.md`).
   Импортируется **лениво** внутри `render()` — без `gigachat`/ключа
   слои 1 и 3 всё равно работают.
   Любой сбой (нет ключа, сеть, пустой ответ) → `formulator_unavailable`
   в лог, роняем на слой 3.

3. **Сырой fallback** — `result_fallback_template` /
   `error_fallback_template` из конфига (`"Готово: {result}"` /
   `"Не удалось выполнить: {error}"`). Срабатывает только если и шаблона
   нет, и формулировщик недоступен. Гарантирует: ответ пользователю
   уходит **всегда**, даже полностью офлайн.

Слой LLM (2) — это bootstrap-этап. Фразы, которые сформулировал GigaChat,
дописываются в `output/dataset.jsonl` (`source: "llm_api"`) — материал
для будущей локальной модели-формулировщика, по аналогии с датасетами
классификатора и SWL. Фразы из шаблонов туда не идут — это не
«учительский» сигнал.

## phrases.json — контент, не настройки

Таблица шаблонов лежит **рядом с кодом** (`system/outputstructurizer/phrases.json`),
под гитом, правится руками. Не в `user/configs/` — потому что это не
параметры процесса, а контент: одно место крутить формулировки и тон, и
оно же — будущие few-shot примеры для формулировщика. `user/configs/outputstructurizer.json`
держит только параметры процесса (интервал, пути, шаблоны последнего
fallback, уровень привилегий).

Нет файла / битый → пустая таблица + предупреждение, всё уходит в слои
2–3.

## Заявка в аудио

`system/audio/tasks/<task_id>.json`, атомарно (temp + rename), имя =
`task_id` (уже уникален и по времени → очередь читается по порядку).
Поля:

| Поле | Смысл |
|---|---|
| `task_id`, `goal`, `status` | сквозная корреляция с задачей ядра |
| `text` | итоговая фраза для произнесения |
| `privilege_level` | **всегда 2** для ответов модулей пользователю. Задел под приоритетную очередь настоящего аудио-демона (будильник, критическая ошибка, ambient — другие уровни), см. `../audio/audio_design.md`. Пока константа из конфига. |
| `source` | каким слоём получена фраза: `template` / `llm` / `fallback` (для отладки и статистики) |
| `source_text` | исходная фраза пользователя — на будущее (тон/скорость озвучки) |
| `kind` | `"tts"` — тип заявки под будущую приоритетную очередь |
| `ts` | время формулировки |

Разобранный файл из `queue/` удаляется (как ядро удаляет разобранный
`goal.json`).

## Решения

- **Протухшее на старте.** Файлы, уже лежащие в `queue/` на момент
  старта демона, — устаревшие ответы (система была выключена/
  перезапущена). Озвученный ответ полезен только свежим, а не «пачкой за
  час». Их не произносим — переносим в `queue/stale/` с логом
  `stale_results_discarded`. Дальше реагируем только на файлы,
  появившиеся после старта. (Это НЕ тот же приём, что «пропустить по
  mtime» у классификатора/SWL — там один файл-последнее-значение, тут
  настоящий бэклог дискретных задач; поэтому явный перенос, а не
  сравнение mtime.)
- **Дедуп** — множество `task_id`, виденных за текущий запуск: тот же
  `task_id` дважды не произносим. Множество не ограничено по размеру
  (task_id — короткие строки, масштаб хобби); ограничить, если когда-то
  понадобится.
- **Один потребитель на очередь.** `queue/` рассчитана ровно на один
  запущенный `outputstructurizer` (так и делает `smos.py`). Два
  параллельных экземпляра разберут один файл дважды (оба схватят его до
  `unlink`) — как и `core` с `goals/`, это свойство файловой очереди, не
  чиним. Отдельный тонкий случай: если процесс убить `SIGKILL` во время
  вызова GigaChat (`phrasing.render` блокируется там ~секунды, а
  `seen.add`/`unlink` — после), файл в `queue/` переживёт и на
  перезапуске обработается заново → дубль в озвучке и в `dataset.jsonl`.
  Дёшево смягчить (переносить файл в in-progress-имя до вызова) —
  отложено: `SIGINT`/`SIGTERM` (штатная остановка, в т.ч. из `smos.py`)
  этот код не задевают, только жёсткий `SIGKILL`.
- **Битый файл** → `queue/rejected/` с суффиксом-uuid и `WARNING`
  (как `goals/rejected/` у ядра) — не крутится в очереди вечно, не
  пропадает молча.
- **Ошибку тоже проговариваем.** `status == "error"` идёт теми же тремя
  слоями (шаблон `_error` → GigaChat с промтом про ошибку → шаблон
  `error_fallback_template`). «Не смог посчитать: деление на ноль» —
  это ответ, а не молчание.

## Вне рамок v1

- **Поле `speech` от модулей** (слой 0 из `audio_design.md`) — требует
  правок в `planner.achieve()` и `task_runner`, и добавки в протокол
  модулей. Отдельно, если понадобится точный дословный путь для
  конкретного модуля.
- **`goal: null` от SWL** (нераспознанная команда) — дыра на стороне
  SWL (сейчас `no_intent_match` в лог), не здесь.
- **Дистилляция** формулировщика в локальную модель — накопление
  `dataset.jsonl` идёт, сам цикл (shadow → offline) — потом.

## Открыто

- Где проходит граница «готовый шаблон / нужна формулировка GigaChat» —
  сейчас просто «есть ключ в phrases.json или нет». Может, флаг в
  манифесте модуля, может, по goal-ключу списком.
- Формат `result` в промпт формулировщика: сырой JSON (сейчас) или
  лёгкая предобработка.
- Оставлять ли `_speech`-подобный контекст (`state`) в заявке для аудио
  целиком — сейчас кладём `source_text`, `state` не кладём (аудио он не
  нужен).
- Канал приёма у аудио: папка (сейчас) против сокета — общий открытый
  вопрос выходной стороны.
