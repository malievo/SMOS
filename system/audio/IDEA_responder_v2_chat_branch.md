# Формулировка ответа через ветку chat — responder v2 (идея)

**Статус: набросок, 2026-08-28. НЕ в текущий цикл.** Сейчас делаем
простой responder v1 (шаблон / `str(result)` + `spd-say`) — см.
[`audio_design.md`](audio_design.md), раздел «v1: responder». Этот файл —
чтобы идея не потерялась, пока руки не дойдут.

## Суть

Синтез речи — это, по сути, уже работа ветки **chat**: там всё равно
нейросеть-«друг» решает, ЧТО сказать. Значит, не надо отдельно
форматировать ответ шаблоном в responder и не надо звать LLM из
responder напрямую.

После того как ядро выполнило команду (`system/core/tasks/<id>/state.json`,
`status: done`) — отдаём результат в ветку chat как **системное
сообщение**, а не реплику пользователя:

```
[Сообщение от системы] Выполнилась команда <goal> с результатом <result>.
Придумай текст, чтобы сообщить это пользователю.
```

Ветка chat придумывает фразу, она уходит в TTS. Всё.

## Зачем так

- **Один вход в нейросеть на весь проект.** Не размазываем вызовы LLM по
  responder, по модулям (поле `speech` из развилки A в `audio_design.md`),
  по SWL. Ветка chat — единственное место, которое знает про
  «друга»-нейросеть и про то, как с ней говорить.
- **Живые ответы**, с учётом персоны и памяти, а не «шаблон по
  goal-ключу».
- **`goal: null` от SWL** (команду не распознали) — туда же: ветка chat
  своим голосом отвечает «не могу это выполнить», отдельной дыры не
  остаётся.

## Что для этого нужно (поэтому v2, а не сейчас)

- Ветка **chat как процесс**: намерение, память (долгая / персона), сам
  вызов нейросети. Это большое отдельное направление.
- **Протокол системных сообщений** в chat: на вход не только реплики
  пользователя, но и «от системы: команда выполнена, вот результат».
- **Дистилляция**, как у классификатора и SWL: bootstrap на облаке
  (GigaChat) → накопление датасета → локальная модель. Для генерации
  ответов это тяжелее классификации — отдельный вопрос, потянет ли
  локальная модель, или ветка chat навсегда останется облачной.

## Связь с v1 и с развилкой из audio_design.md

- v1 responder не мешает: v2 просто заменяет шаг «сформулировать фразу» —
  с шаблона на «спросить ветку chat». Точка съёма (`tasks/`) и вывод
  (TTS / `spd-say`) — те же.
- **C не отменяет A, а ставит её первой в цепочке.** Развилка A/B из
  `audio_design.md` («поле `speech` у модулей» против «шаблон в
  responder») не закрывается, а превращается в fallback-цепочку:
  `speech` от модуля (точный, дословный путь — там, где число нужно
  сказать ровно) → ветка chat (живая формулировка, персона, память) →
  тупой шаблон по goal-ключу (когда chat недоступна). `speech` остаётся
  необязательным: его дают только модули, которым важна точная
  формулировка; всем остальным ответ придумывает chat. Центрального NLG
  внутри ядра по-прежнему нет.

## Гибрид — это конечная форма, а не переходный fallback

Не «пока делаем шаблон, потом всё через chat», а навсегда так:
дёшево-детерминированные ответы (время, результат вычисления,
«готово») — шаблоном или через `speech` модуля, мгновенно и дословно;
через ветку chat — там, где ответ реально нужно *сформулировать*
(объяснить, смягчить, ответить на `goal: null`, связать с контекстом
разговора). Причина — не скорость (GigaChat отвечает быстро, он для
того и в SWL в горячем пути; онлайновый TTS ближайших версий тоже
быстрый), а **точность и стоимость**: LLM, проговаривая «15:47», может
округлить или потерять «вечера», и гонять облако на каждое «который
час» — лишние деньги и лишняя точка отказа. Где проходит граница
«простое / нужна формулировка» — открытый вопрос (по goal-ключу?
по флагу в манифесте? по наличию `speech`?).

## Открытые вопросы

- **Недоступность ветки chat** (нет ключа, офлайн, локальная модель не
  готова) → fallback на шаблонный responder v1 (последнее звено цепочки
  выше).
- **Формат передачи `result`**: сырой JSON прямо в промпт или лёгкая
  предобработка перед этим.
