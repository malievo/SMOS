# Аудио-демон SMOS — дизайн (не реализовано)

**Статус: набросок по итогам обсуждения 2026-08-27/28. Кода нет,
папка `system/audio/` заведена под него.** Стоит рядом с `system/core/`,
`system/fwl/`, `system/swl/`.

## Зачем отдельный процесс, а не «каждый модуль играет сам»

**Динамик один.** Как только в системе есть и музыка, и проговаривание
(ответ на вопрос, критическая ошибка, будильник) — кто-то должен
разрешать конкуренцию за звук: приглушить музыку, сказать, вернуть
громкость. Эта логика обязана жить в одном месте. «Каждый модуль сам»
разваливается на первом совпадении и дублирует код воспроизведения
везде.

**Это та же форма, что демон логов.** Системный процесс, который владеет
ресурсом (там — файлы логов, тут — звуковое устройство), остальные шлют
ему заявки fire-and-forget. По тесту «модуль vs системный процесс»
(см. `../swl/swl_design.md`) аудио-демон — процесс, не модуль, не часть
SWL-пайплайна.

**Это начало выходной стороны SMOS.** FWL — вход (микрофон → текст →
классификация). Выхода нет вообще: ядро считает результат в
`system/core/tasks/<id>/state.json`, и его никто не озвучивает.
Аудио-демон — первый кусок выхода.

## Форма

- **Владеет устройством вывода.**
- **Приоритетная очередь** элементов воспроизведения:
  `{kind: "tts" | "sfx" | "music", priority, payload}` (payload — текст
  для синтеза / путь к файлу / список треков).
- **Вытеснение и приглушение.** Высокоприоритетный `tts` (ответ
  пользователю, ошибка) ставит `music` на паузу или гасит громкость,
  проговаривает, восстанавливает. Будильник — поверх всего.
- **Приём заявок** — папка `system/audio/queue/` (файлы, как
  `system/core/goals/`) либо сокет. Отправитель (модуль, ядро, будущий
  «озвучиватель ответов») не блокируется на времени проигрывания.
- **Управление** музыкальным «каналом» (пауза/продолжить/след/стоп/
  громкость) — те же заявки с управляющими глаголами.
- **Состояние на диске** — `system/audio/state.json`: что играет
  сейчас, содержимое очереди, громкость. Читается без обращения к
  процессу — как везде в SMOS.
- **Конфиг** — `user/configs/audio.json` (устройство, громкость по
  умолчанию, уровни приглушения) по общей схеме `user/configs/`.

## TTS

Синтез речи и воспроизведение — внутреннее дело демона: он либо
дёргает движок TTS сам, либо вызывает отдельный TTS-модуль, и уже
результат кладёт в очередь как `kind: "tts"`. Выбор движка и разделение
«синтез vs проигрывание» — при реализации.

## Музыкальный модуль в этой картине

Не «звуковая система», а **диджей/библиотекарь**: разобрать «включи
что-нибудь спокойное» → список треков, глаголы управления, дозаправка
очереди по мере проигрывания. PCM в динамик — не его работа, он пушит
очередь в аудио-демон. Музыкальный модуль — сессионный (повышается до
процесса на время воспроизведения), см. `../core/core_design.md`,
раздел «Долгоживущие модули: сессии».

## Рядом, но отдельно: формулировка ответа

Кто превращает завершённую задачу (`tasks/<id>/state.json`, `status:
done`) в произнесённую фразу — это отдельный слой, не аудио-демон.
Аудио-демон только проигрывает то, что ему дали; превратить
`{"temperature_c": 21}` в «за окном двадцать один градус» должен кто-то
до него.

**Слоёный fallback (решено 2026-08-28), сверху вниз:**

1. Поле `speech`, которое модуль по желанию возвращает в своём ответе —
   модуль лучше всех знает свой результат.
2. Центральный список шаблонов (`phrases.json`, ключ — goal-ключ,
   подстановка из `result`). НЕ шаблон внутри каждого модуля: одно
   место крутить формулировки и тон, и он же — few-shot примеры для
   формулировщика потом. Для подтверждений команд (результаты
   структурны и однообразны) шаблон — это **правильно**, а не
   компромисс.
3. Формулировщик: GigaChat на bootstrap → потом персона chat-ветки.
   Когда шаблона нет, на ошибках, или когда «стоит сказать
   по-человечески».
4. `str(result)` — если формулировщик недоступен.

Это ложится на **уровни оффлайна** проекта: слои 1–2 оффлайн и
мгновенны (уровень 1 — командная спина: wake, STT, классификатор, SWL,
GOAP, исполнение, шаблонные подтверждения), слой 3 — онлайн-first и,
возможно, навсегда (уровень 2 — красноречивый друг: персона, память
разговора).

Отдельная идея, которую автор фиксирует рядом: гнать результат команды
**через** chat-ветку целиком (системный промт «команда X выполнена,
результат Y, сформулируй для пользователя») — один генератор языка на
весь проект. См. `IDEA_responder_v2_chat_branch.md`. Та же цена: нужна
сама chat-ветка, и LLM-вызов на каждое подтверждение.

## v1: замыкание цикла (следующая задача, отдельный чат)

Стадия «формулировка» и стадия «динамик» — **два отдельных процесса**
(решение автора, заранее): один приводит ответ в человеческий вид,
другой владеет звуком.

Ядро уже отдаёт результат дальше (реализовано 2026-08-28, см.
`../core/core_design.md` раздел «Отдача результата дальше»): завершив
задачу, `task_runner` кладёт компактный файл-результат
(`task_id`, `goal`, `status`, `result`, `error`, `state`, `source_text`,
`ts`) в `system/outputstructurizer/queue/`.

Что достроить (не в этом чате):

- **`system/outputstructurizer/`** — системный процесс: поллит свою
  `queue/`, превращает `result` / `error` в фразу (слоёный fallback
  ниже), кладёт заявку на синтез в очередь аудио. Дедуп по `task_id`,
  файлы до старта пропускает (приём классификатора/SWL). Разбор файла
  удаляет.
- **`system/audio/`** — системный процесс с доступом к динамику: поллит
  свою очередь заявок, произносит. v1 — `spd-say` (speech-dispatcher,
  на машине разработки есть, fire-and-forget), команда и вкл/выкл в
  `user/configs/audio.json`, команды нет / упала → просто печать, не
  падаем. Это НЕ полный демон выше (без приоритетов, приглушения,
  музыки) — только «сказать текст».
- Строки в `smos.py`:
  `Proc("outputstructurizer", ...)`, `Proc("audio", ...)`.
- Тест сквозняком: SWL → ядро → `outputstructurizer/queue/` →
  формулировка → очередь аудио → произнесено.

### Формулировка в v1

Слоёный fallback выше уже решён. v1 берёт слои **1, 2, 4** и
пропускает слой 3 (LLM-формулировщик) — его подключают, когда появится
chat-ветка:

1. `speech` от модуля: `{"status":"ok","data":{...},"speech":"за окном 21 градус"}`.
   `planner.achieve()` протаскивает `speech` от модуля, который произвёл
   сам ключ цели (не промежуточного), в `state.json` и оттуда в
   файл-результат (место под `speech` там уже оставлено).
   `outputstructurizer` его берёт как есть. Небольшая правка в
   `achieve()` + `speech` в паре модулей для демо + строчка в протоколе
   `manifest_design.md`.
2. Нет `speech` → шаблон из `phrases.json` по goal-ключу.
3. *(пропущено в v1)*
4. Нет шаблона → `str(result)`.

### Вне рамок v1

`goal: null` от SWL (нераспознанная команда → «не могу это выполнить»)
— это дыра на стороне SWL (сейчас просто лог `no_intent_match`), не
`outputstructurizer`. Отдельно.

## Когда строить

Полный демон выше — с первым «сказать вслух» сверх простого ответа
(очередь звуков, музыка, приглушение). `responder` из раздела v1 — уже
сейчас, это и есть первое «сказать вслух».
