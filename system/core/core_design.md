# Ядро SMOS — модель выполнения задач

Статус: черновик по итогам обсуждения 2026-08-26, ничего ещё не
реализовано. Про регистрацию/вызов модулей — см.
[`module_init/manifest_design.md`](module_init/manifest_design.md);
про место ядра в общей картине FWL/SWL — см.
[`../swl/swl_design.md`](../swl/swl_design.md).

## Требование: ядро асинхронно

Ядро — постоянно работающий системный процесс (см. `swl_design.md`),
который принимает цели от SWL. Требование автора: приём новой цели и
создание под неё задачи **не должны блокировать** приём следующих
целей — пока одна задача выполняется (возможно, несколько секунд,
несколько вызовов модулей подряд), ядро должно быть готово тут же
принять и начать вторую, третью и так далее, параллельно.

## Модель: поток на задачу

- Главный цикл ядра только: принимает цель от SWL → создаёт папку
  задачи с уникальным id → запускает отдельный `threading.Thread`,
  который целиком ведёт эту задачу → сразу же возвращается к приёму
  следующей цели. Никогда не ждёт завершения задачи.
- Внутри потока задачи код **обычный последовательный/блокирующий**:
  вызвал модуль (см. `subprocess.run` в `manifest_design.md`) →
  дождался ответа → если `status: missing` — пошёл искать модуль,
  который производит недостающее → дождался → вызвал исходный модуль
  снова, уже с полными данными → получил `status: ok` → задача
  завершена. Блокируется только этот конкретный поток, не ядро в целом.

**Почему потоки, а не `asyncio`.** Узкое место — не вычисления в
Python, а ожидание внешнего процесса (subprocess на каждый вызов
модуля). Пока Python ждёт завершения дочернего процесса, он отпускает
GIL — то есть параллелизм между потоками реальный, без необходимости
переписывать логику задачи в `async`/`await`-стиле. Поток можно писать
как прямолинейный последовательный код, ровно как задача и мыслится
(шаг за шагом, с ожиданием на каждом шаге) — `asyncio` решал бы ту же
задачу, но ценой смены стиля кода без выигрыша, раз узкое место и так
уже не блокирует остальные потоки.

## Память задачи — файл, не shared memory

Каждая задача — папка `system/core/tasks/<task_id>/` с `state.json`:
исходная цель, что уже известно (собранные параметры), чего ещё не
хватает, на каком шаге задача сейчас, финальный статус. Обновляется
атомарно (temp-файл + rename), тем же приёмом, что уже используется в
`rvs`/классификаторе для их output-файлов.

Важно: поток задачи **не** пишет в какую-то общую in-memory структуру
главного цикла ядра (реестр активных задач, счётчики и т.п.) — это
сразу вопросы потокобезопасности и блокировок. Вместо этого поток
просто обновляет свой `state.json`, включая `"status": "done"` по
завершении. Всё, что хочет узнать про задачу (главный цикл, в будущем —
модуль синтеза речи, который должен сообщить пользователю о готовности)
— читает этот файл, а не спрашивает поток напрямую. Общение между
частями системы остаётся файловым, как и во всём остальном SMOS —
не нужно вводить новый механизм синхронизации специально для этого.

## Планировщик: разрешение цели рекурсией (backward chaining)

Внутри потока задачи (см. выше) сама логика "дойти до цели, докупив по
дороге недостающие данные через другие модули" — это рекурсивное
разрешение цели, backward chaining: идём от цели назад к тому, что для
неё нужно, рекурсивно, пока не упрёмся в уже известное.

```python
def achieve(target_key, state):
    """Возвращает значение target_key, при необходимости вызывая цепочку модулей."""
    if target_key in state:
        return state[target_key]          # уже есть — ничего вызывать не надо

    action = find_action_that_produces(target_key)   # ищем в реестре модулей
    if action is None:
        raise Exception(f"никто не производит {target_key}")

    # сначала обеспечиваем ВСЕ needs этого действия — рекурсивно
    params = {}
    for need in action.needs:
        params[need] = achieve(need, state)

    response = call_module(action, params)            # subprocess.run(...)

    if response["status"] == "missing":
        # модуль сам, в рантайме, попросил что-то сверх заявленных needs
        for key in response["missing"]:
            state[key] = achieve(key, state)
        response = call_module(action, {**params, **state})   # повторный вызов

    if response["status"] == "ok":
        state.update(response["data"])
        return state[target_key]
    raise Exception(response.get("error"))
```

Задача просто вызывает `achieve(goal, {})` один раз. Пример на
weather/location: `weather_forecast` нет в state → находим модуль
weather (needs=["city"]) → рекурсивно `achieve("city", ...)` → города
тоже нет → находим location (needs пустой) → вызываем → получаем
город → возвращаемся наверх → вызываем weather уже с городом →
получаем прогноз.

**Циклы.** Если манифесты образуют замкнутый круг (A требует B, B
требует A) — рекурсия уйдёт в бесконечность. Нужна защита — множество
"сейчас разрешаю X" по ходу рекурсии; повторное попадание в него — это
ошибка, а не зависание. Пока не реализовано, но забыть нельзя.

**Несколько модулей производят одно и то же.** Алгоритм выше берёт
первый найденный кандидат без дополнительной логики выбора. Как
выбирать умнее (например предпочитать того, у кого needs уже все
известны) — открытый вопрос на будущее, не решается сейчас.

**Реализовано** в `planner/planner.py` (2026-08-26): `achieve()` +
`call_module()` (subprocess по протоколу из `manifest_design.md`) +
`find_action_that_produces()` + защита от циклов через `_resolving`.

Проверено (2026-08-26, добавлены тестовые модули `weather` + `location`
в `system/modules/`): многошаговая цепочка работает — цель
`weather_forecast` с пустым состоянием сама находит `location` за
городом, потом вызывает `weather` уже с городом; если город уже
известен заранее — `location` не вызывается вообще (короткое
замыкание по state отработало верно). **Всё ещё не проверено** — ветка
`status: missing` внутри `achieve()` (когда модуль просит что-то сверх
заявленных needs, а не то, что штатно резолвится через needs заранее)
— специально для этого нужен модуль, который в рантайме запрашивает
параметр, не объявленный в своём же манифесте; ни один из тестовых
модулей так не делает, это отдельный сценарий на будущее.

**Параллельное разрешение needs — сознательно не делаем сейчас.**
Технически, если у действия несколько независимых needs (не зависящих
друг от друга по данным), их можно было бы резолвить параллельно
(поток на каждый need), как это делают системы сборки (Make, Bazel) —
а не строго по очереди в `for`-цикле. Это настоящая альтернатива, не
надуманная, но добавляет сложность (частичные отказы, объединение
результатов) ради выигрыша, которого пока негде проверить — цепочки
needs пока короткие, модулей мало. Внутри одной задачи выполнение
последовательное; разные задачи (разные потоки) и так уже выполняются
параллельно друг другу — это отдельный, более крупный уровень
параллелизма, уже решённый выше.

## Реализовано (2026-08-26)

`task_runner/task_runner.py`: `create_task(goal, initial_state, graph)`
создаёт `system/core/tasks/<task_id>/state.json` и запускает
`threading.Thread`, сразу возвращая `task_id` — не дожидаясь
выполнения. Поток вызывает `planner.achieve()`, пишет `status`
(`running` → `done`/`error`), финальный `state` и `result` обратно в
файл. `read_state(task_id)` читает файл — так другие части системы
узнают о задаче, а не спрашивая поток напрямую.

Проверено: две задачи, вторая (`echoed_text`) создаётся сразу вслед за
первой (`weather_forecast`, многошаговая), без ожидания — обе
возвращают управление за ~0 сек, обе доходят до `status: done` с
верным результатом, `state.json` на диске содержит и накопленное
состояние (город + прогноз), и финальный результат.

`task_id` — время создания + короткий случайный хвост
(`20260826_183343_0a102f44`), для читаемости списком папок глазами и
гарантии уникальности при параллельном создании.
