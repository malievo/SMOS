# Как работает ядро SMOS — от цели до результата

Это не документ решений (для этого — `core_design.md`,
`module_init/manifest_design.md`) — это связный рассказ, как всё уже
реализованное работает вместе, от старта до готового результата.
Написано 2026-08-26 по факту того, что уже собрано и проверено.

## Действующие лица

- **`module_init/`** — при старте находит модули и строит граф
  возможностей.
- **`planner/`** — по цели ищет путь в этом графе и выполняет его,
  вызывая модули.
- **`task_runner/`** — оборачивает один вызов планировщика в отдельную
  задачу (поток + папка на диске), чтобы ядро не блокировалось.

Дальше — по порядку, как это происходит в реальности.

## 1. Старт: ядро узнаёт, что оно умеет

Перед тем как принять хоть одну цель, ядро один раз сканирует папки
модулей:

```python
modules = module_registry.scan()          # обходит system/modules/ и modules/
graph = module_registry.build_registry(modules)
```

`scan()` заходит в каждую подпапку `system/modules/` и `modules/`
(корень проекта), ищет `manifest.json`, проверяет его структуру
(`manifest.py`). Манифест без обязательных полей — не ошибка всего
запуска, а предупреждение в лог и пропуск конкретного модуля.

`build_registry()` разворачивает список манифестов в **плоский граф
действий** — не по модулям, а по конкретным командам:

```json
{
  "get_city":    {"module": "location", "needs": [],      "produces": ["city"],             "entrypoint": [...], "cost": 1},
  "get_weather": {"module": "weather",  "needs": ["city"], "produces": ["weather_forecast"], "entrypoint": [...], "cost": 1}
}
```

Это и есть тот граф, в котором дальше будет искать путь планировщик.
Больше сканирование не повторяется до перезапуска ядра (осознанное
решение — без hot-reload, см. `swl_design.md`).

## 2. Ядро получает цель, не блокируясь

SWL (разбор фразы в цель) ещё не построен — сейчас цель на вход даётся
вручную, для проверки. В будущем именно SWL будет вызывающей стороной,
но интерфейс уже не изменится:

```python
task_id = create_task("weather_forecast", {}, graph)
```

`create_task()` делает три вещи и сразу возвращает `task_id`, не
дожидаясь результата:

1. Создаёт папку `system/core/tasks/<task_id>/` — id вида
   `20260826_183343_0a102f44` (время + случайный хвост — читаемо
   глазами, гарантированно уникально).
2. Пишет туда `state.json` со стартовым состоянием
   (`status: "running"`, `state` = то, что уже известно на входе,
   в этом примере — ничего).
3. Запускает `threading.Thread`, который дальше сам доведёт задачу до
   конца — и сразу возвращает управление.

Если в этот момент придёт вторая цель — `create_task()` для неё
отработает точно так же, немедленно, не дожидаясь первой. Это и есть
"ядро асинхронно": блокируется не сам приём цели, а только конкретный
поток внутри своей собственной задачи.

## 3. Поток задачи ищет путь: `achieve()`

Внутри потока — вызов `planner.achieve(goal, state, graph)`. Это
рекурсивный алгоритм (backward chaining — идём от цели назад, к тому,
что для неё нужно). Проследим его пошагово на примере
`achieve("weather_forecast", {}, graph)`:

**Шаг 1.** `"weather_forecast"` нет в `state` (state пустой). Нужно
найти, кто его производит — ищем в графе action, у которого
`"weather_forecast"` в `produces`. Находим `get_weather` (модуль
`weather`), у него `needs: ["city"]`.

**Шаг 2.** Прежде чем вызвать `get_weather`, нужно обеспечить его
needs. `"city"` тоже нет в `state` — рекурсивно вызываем
`achieve("city", state, graph)`.

**Шаг 3 (внутри рекурсии).** Ищем, кто производит `"city"` — находим
`get_city` (модуль `location`), у него `needs: []` — обеспечивать
нечего, можно вызывать сразу.

**Шаг 4.** Вызываем `location`: `call_module()` запускает
`python3 main.py get_city '{}'` как отдельный процесс, ждёт
завершения, читает stdout: `{"status": "ok", "data": {"city": "Москва"}}`.
`state` пополняется: `state["city"] = "Москва"`. Рекурсия возвращает
`"Москва"` наверх, на шаг 2.

**Шаг 5.** Теперь `params = {"city": "Москва"}` собраны, вызываем
`weather`: `python3 main.py get_weather '{"city": "Москва"}'`. Ответ:
`{"status": "ok", "data": {"weather_forecast": {...}}}`. `state`
пополняется данными прогноза.

**Шаг 6.** `achieve()` возвращает `state["weather_forecast"]` — готовый
результат — в поток задачи.

Если бы `state` заранее уже содержал `"city"` (например SWL в будущем
вытащил его прямо из фразы "погода в Питере") — шаги 2–4 бы просто не
случились: `achieve("city", ...)` увидел бы город уже в `state` и
вернул его без единого вызова `location`. Путь строится по тому, чего
реально не хватает, а не по жёсткому сценарию.

### Если модуль просит больше, чем заявлено в needs

Отдельный случай — модуль в рантайме отвечает
`{"status": "missing", "missing": ["x"]}`, хотя `"x"` не было в его
`needs`. Тогда `achieve()` рекурсивно добывает и `"x"` тем же способом,
и повторяет вызов модуля уже с ним. Это подстраховка сверх
статического манифеста — на практике пока не встречалось ни в одном
тестовом модуле.

### Если пути нет вообще

Если ни один action в графе не производит нужный ключ —
`achieve()` бросает `PlanningError` с понятным сообщением
(`"никто не производит 'x'"`), а не зависает и не падает молча. Так же
он защищён от зацикливания (если бы манифесты образовали замкнутый
круг needs) — отслеживает, что уже пытается разрешить прямо сейчас, и
не даёт себе войти в бесконечную рекурсию.

## 4. Вызов модуля: что происходит физически

`call_module()` — это единственное место, где ядро реально запускает
чужой код, и делает это изолированно:

```python
subprocess.run(
    [*entrypoint, command, json.dumps(params)],
    cwd=module_dir,
    capture_output=True,
    text=True,
    timeout=5,
)
```

Модуль — отдельный процесс. Он получает команду и параметры через
`sys.argv`, печатает единственный JSON-объект в stdout и завершается.
Если он упал (ненулевой код возврата), завис дольше таймаута, или
напечатал не-JSON — `call_module()` возвращает `{"status": "error", ...}`,
и это не роняет ни поток задачи, ни тем более ядро целиком — падение
одного модуля это просто неудачный шаг одной конкретной задачи.

## 5. Задача завершается — снова через файл

Когда `achieve()` вернул результат (или бросил `PlanningError`) — поток
задачи обновляет `state.json`:

```json
{
  "task_id": "20260826_183343_0a102f44",
  "goal": "weather_forecast",
  "state": {"city": "Москва", "weather_forecast": {...}},
  "status": "done",
  "result": {...},
  "error": null
}
```

`status` — `"error"`, если `PlanningError` — с текстом причины в
`"error"`. Никто не спрашивает поток напрямую, всё через этот файл —
если в будущем модулю синтеза речи нужно будет узнать, что задача
готова, он прочитает этот же `state.json`.

## Итоговая картина одним взглядом

```
SWL даёт цель
      │
      ▼
create_task() ── создаёт папку задачи, запускает поток, СРАЗУ возвращает управление
      │                                                   (ядро свободно принимать следующую цель)
      ▼ (внутри потока, независимо от остальных)
achieve(goal, state, graph)
      │
      ├─ цель уже в state? ── да ──→ вернуть как есть, ничего не вызывать
      │
      └─ нет → найти action в графе, который её производит
                │
                ├─ для каждого need этого action → achieve(need, ...) рекурсивно
                │
                └─ call_module() → subprocess → JSON ответ (ok / missing / error)
                        │
                        ├─ ok      → записать данные в state, вернуть результат
                        ├─ missing → добыть недостающее рекурсивно, повторить вызов
                        └─ error   → PlanningError наверх
      │
      ▼
state.json обновлён: status done/error, финальный state и result
```

## Что сюда пока не входит

- Откуда берётся сама цель и начальный `state` — задача SWL, ещё не
  построен (см. `../swl/swl_design.md`).
- Выбор между несколькими модулями, производящими одно и то же —
  сейчас берётся первый найденный, без сравнения (см. открытый вопрос
  в `core_design.md`, там же — про `cost`, который пока никем не
  используется).
- Параллельное разрешение независимых needs внутри одной задачи —
  сознательно не делается, см. `core_design.md`.
