# Манифест модуля SMOS — дизайн

Статус: черновик по итогам обсуждения 2026-08-25/26, ничего ещё не
реализовано. Формат манифеста и запуск модулей как отдельных процессов
согласованы; протокол вызова (что именно передаётся модулю и что он
возвращает) — обсуждается следующим.

## Зачем манифест

Единый артефакт, используемый дважды: и как запись в реестре модулей
(что core знает о модуле после сканирования `system/modules/` +
`modules/` при старте), и как узел графа для планировщика (needs/produces
для GOAP-поиска, см. [`../../swl/swl_design.md`](../../swl/swl_design.md)).

## Модули — отдельные процессы, не import

Решено: core вызывает модуль как **отдельный процесс**, не импортирует
его код к себе в интерпретатор. Причины:

- **Изоляция сбоя.** Тот же принцип, что уже применён в проекте для
  логирования (UDP, fire-and-forget — сбой одного отправителя не должен
  ронять остальных, см. `logs/PROTOCOL.md`). Если модуль упадёт с
  исключением, это не должно уронить core и всё, что он в этот момент
  обслуживает.
- **Манифест — полный внешний интерфейс.** При импорте core пришлось бы
  знать имя функции внутри чужого файла (reflection в чужой код,
  связанность). При процессном вызове манифест сам по себе полностью
  описывает, как обратиться к модулю снаружи — core никогда не заглядывает
  внутрь.
- Модуль технически может быть не на Python — интерфейс через процесс
  этого не запрещает, хотя сейчас все модули на Python.

Раз вызов разовый (не постоянно работающий процесс, как `rvs`/классификатор,
которым нужен поллинг файлов) — core просто запускает процесс, ждёт
завершения, читает результат. Управление жизненным циклом процесса
целиком у core.

## Формат манифеста

```json
{
  "name": "weather",
  "description": "Погода: текущая и прогноз",
  "entrypoint": {
    "command": ["python3", "main.py"]
  },
  "actions": [
    {
      "command": "get_weather",
      "description": "Текущая погода в городе",
      "needs": ["city"],
      "produces": ["weather_forecast"]
    }
  ]
}
```

- **`name`** — уникальный id модуля. Используется в реестре, в узлах
  графа, совпадает с полем `module` в логах (та же роль, что уже есть у
  classifier/rvs).
- **`description`** — человекочитаемый текст. Планировщику не нужен (тот
  работает только с needs/produces), но задел на будущее для разбора
  фразы в цель — если SWL будет искать нужный модуль по смыслу описания.
- **`entrypoint.command`** — как запустить процесс модуля (базовая
  команда, без параметров вызова — они добавляются поверх, см. протокол
  вызова).
- **`actions`** — список действий, которые умеет модуль. Один модуль
  (одна папка, один процесс) может объявлять несколько действий —
  каждое становится отдельным узлом графа планировщика со своими
  needs/produces, но все запускаются через один и тот же процесс, с
  разным именем команды (`command` внутри action, не путать с
  `entrypoint.command`).
  - `needs` / `produces` — плоские списки строк-ключей, без типов.
    Не усложняем типизацией заранее; общий словарь ключей (что значит
    `"city"`) — вопрос дисциплины при написании модулей (мера от
    автора: называть ключи специфично, `user_city_now`, а не
    `city`, чтобы снизить шанс случайного совпадения), а не
    технического ограничения, пока модулей мало.
  - `cost` — необязательное число, по умолчанию 1 (`manifest.py:
    DEFAULT_ACTION_COST`). Заведено заранее (2026-08-26), хотя сама
    логика выбора между несколькими путями по стоимости пока не
    написана — нечего сравнивать, пока в реестре нет двух путей к
    одной цели. Причина завести поле уже сейчас, а не когда появится
    сама логика: если не завести, при появлении конкурирующих модулей
    придётся задним числом дописывать `cost` во все уже существующие
    манифесты, чтобы новому механизму было на что опереться — а само
    поле дешёвое и ничего не ломает. `registry.py` уже пробрасывает
    его в реестр с дефолтом.

## Регистрация

Core сканирует `system/modules/` и `modules/` (корень проекта) **при
старте**, читает манифест каждой папки, строит реестр действий (каждый
`actions[i]` — отдельная запись с needs/produces + сведения, как
вызвать: `entrypoint.command` + `actions[i].command`). Без динамической
догрузки во время работы — решено ранее, см.
[`../../swl/swl_design.md`](../../swl/swl_design.md).

Реализовано в `manifest.py` (валидация одного манифеста) и `registry.py`
(`scan()` — обход обеих папок, `build_registry()` — плоский реестр
действий). Битый манифест не роняет сканирование остальных модулей —
пропускается с предупреждением в лог и консоль.

**Снимок на диске.** `registry.py` сохраняет результат в
`output/modules.json` (найденные модули) и `output/graph.json` (сам
граф needs/produces) — атомарно (temp+rename), как везде в проекте.
Это не источник истины (им остаётся сканирование папок модулей заново
при каждом старте) — просто копия для чтения глазами и другими частями
системы без запуска Python. Папка `output/` в `.gitignore`, как и
остальные рантайм-данные проекта.

Пока это `modules.json`, не `active_modules.json` — реальной проверки
"модуль может быть вызван" ещё нет (открытый вопрос ниже), поле статуса
активации добавится вместе с самой проверкой, не раньше.

## Открыто

- **Проверка вызываемости модуля.** Сейчас в реестр попадает любой
  модуль с валидным по структуре манифестом — без проверки, что
  `entrypoint.command` реально запускается (существует интерпретатор,
  файл, зависимости и т.п.). Такая проверка и разделение
  найден/провален-валидация/активен — на будущее, не решалось.

## Протокол вызова

### Запуск и передача параметров

```python
import subprocess, json

result = subprocess.run(
    ["python3", "main.py", "get_weather", json.dumps({"city": "Москва"})],
    capture_output=True,
    text=True,
    timeout=5,
)
```

- Первый аргумент `subprocess.run` — **список строк**
  `[entrypoint.command..., action.command, json.dumps(params)]`. Это не
  текстовая команда для шелла — Python напрямую просит ОС создать
  процесс с этим массивом аргументов, шелл не участвует, поэтому
  кавычки/пробелы/кириллица внутри JSON не создают проблем с
  экранированием.
- `capture_output=True` — Python сам ловит stdout/stderr процесса в
  `result.stdout` / `result.stderr`.
- `text=True` — эти поля приходят строками, не байтами.
- `timeout=...` — грубая защита от зависшего модуля: если процесс не
  уложился, Python бросает `subprocess.TimeoutExpired`. В коде на
  сегодня это единственная жёсткая константа (`planner.DEFAULT_TIMEOUT_SEC
  = 5`). **Дальше её планируется заменить на определение зависания по
  признаку жизни — см. отдельный подраздел ниже; статичное число
  `timeout_sec` в манифесте НЕ вводить.**
- `subprocess.run(...)` — **блокирующий** вызов: код не пойдёт дальше,
  пока процесс не завершится или не истечёт таймаут. Это осознанно (см.
  раздел про асинхронность ядра ниже) — блокируется только конкретная
  задача, которая ждёт этот модуль, а не всё ядро целиком.

### Зависание модуля: heartbeat, а не дедлайн (не реализовано)

**Статус: направление по итогам обсуждения 2026-08-27, в коде пока
жёсткий `timeout=5` из `subprocess.run`.**

Проблема с числом в манифесте (`timeout_sec`): длительность модуля — это
не факт, а прогноз, который сам модуль часто дать не может. «Скачай
файл» — 2 КБ или 2 ГБ? «Спроси API» — кэш-хит или холодный запрос? Любое
фиксированное число будет либо слишком тугим (убьёт законную долгую
работу), либо слишком щедрым (зависший модуль висит до потолка).

**Сдвиг: следить не за длительностью, а за признаком жизни.** Зависший
модуль не двигается и ничего не производит; медленный — двигается.

Механизм (когда дойдут руки):

- **Heartbeat в `stderr`.** `stdout` занят контрактом — туда ровно один
  финальный JSON. `stderr` свободен, и родитель держит его трубой. Долгий
  модуль пишет в `stderr` что угодно по ходу дела (точку, слово,
  процент). Простой модуль не пишет ничего и быстро завершается — на
  него это не влияет.
- **Окно тишины вместо дедлайна.** Планировщик считает, сколько модуль
  молчит И не завершился. Строка в `stderr` → счётчик сброшен. Молчит
  дольше `idle_timeout` (порядка 15–30 c — с запасом на один обычный
  блокирующий вызов) → вот теперь зависший, убиваем.
- **Жёсткий потолок** — отдельно, абсолютный максимум (1–2 мин), выше
  которого убиваем в любом случае, даже если heartbeat исправно капает
  (от зациклившегося модуля, который спамит точками).
- В логе при убийстве различать причину: `молчал N c` против `превысил
  потолок`.
- **Цена в коде:** `subprocess.run(timeout=)` → `subprocess.Popen` +
  цикл надзора (читаем `stderr` построчно, сами считаем время).

Неудобный случай — чистое ожидание сети (нет CPU, нет вывода): это
**ответственность модуля** — не делать неограниченных блокирующих
вызовов, у своего HTTP-запроса ставить свой таймаут. `idle_timeout`
подбирается так, чтобы перекрывать один нормальный сетевой круг;
heartbeat нужен только для работы честно длиннее этого.

Необязательный слой на будущее: писать фактическую длительность каждого
вызова в `logs/raw/<module>/` и брать `idle_timeout`/потолок для модуля
из его же истории (`p99 * 2` и т.п.), а не из глобальной константы — в
духе адаптивных порогов классификатора. Минус — холодный старт.

Итог по контракту модуля: вместо «объяви, сколько ты выполняешься»
(обещание, которое не сдержать) — «**если ты медленный, докажи, что
жив**». Это про возможность, а не про поведение — тот же стиль, что
`needs`/`produces`.

Модуль внутри читает `sys.argv`:

```python
import sys, json

command = sys.argv[1]              # "get_weather"
params = json.loads(sys.argv[2])   # {"city": "Москва"}

# ...своя логика/парсер модуля, вызывает нужную функцию...

print(json.dumps({"status": "ok", "data": {"weather_forecast": {...}}}, ensure_ascii=False))
```

### Формат ответа

Модуль печатает **ровно один** JSON-объект в stdout как единственный
вывод (никаких отладочных print — для этого свой `log_client.py`, как
уже принято в проекте). Core читает его так: `json.loads(result.stdout)`.
Три формы:

```json
{"status": "ok", "data": {"weather_forecast": {...}}}
```
```json
{"status": "missing", "missing": ["city"]}
```
```json
{"status": "error", "error": "текст ошибки"}
```

`missing` — сигнал "не хватает параметра", без которого планировщик не
может решить, какую подзадачу породить. `error` — модуль попытался и не
смог (не путать с "не хватает данных" — это про сам ход выполнения).

Перед парсингом стоит проверить `result.returncode` — если не 0,
модуль упал (трейсбек в `result.stderr`), это отдельный случай отказа,
не валидный JSON-ответ.

### Почему stdout, а не файлы, как в FWL

`rvs`/классификатор — постоянно работающие, независимые друг от друга
процессы: тот, кто читает результат, не контролирует, когда именно
писатель его создаст, поэтому нужен файл, который читатель периодически
проверяет (поллинг). Здесь иначе: core сам запускает модуль именно
сейчас и сам же сразу ждёт его завершения — это синхронный
запрос-ответ внутри одной задачи, ближе к вызову функции, чем к
отношениям rvs/classifier. Через файлы пришлось бы городить лишнее
(уникальное имя файла на вызов, чтобы параллельные вызовы не затирали
друг друга, и решать ту же проблему "не прочитать файл на середине
записи", которую rvs/classifier решают через temp+rename). При stdout
эта проблема не существует в принципе: `subprocess.run` не возвращает
управление, пока процесс не завершится и весь его stdout не будет
пойман целиком — прочитать "недописанную половину" физически
невозможно.
