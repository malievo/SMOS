# Шаблоны параметров модулей (`params`) — дизайн

**Статус: реализовано 2026-09-10 (bootstrap-версия).** Журнал решений +
что построено (§13 в конце). Не финальная спецификация.

Родственное: [`swl_design.md`](swl_design.md) (SWL в целом, каталог целей,
открытый вопрос «как из фразы получить цель с параметрами» — этот
документ его продолжает), [`../core/module_init/manifest_design.md`](../core/module_init/manifest_design.md)
(формат манифеста, `needs`/`produces`), [`../../local_brain_design.md`](../../local_brain_design.md)
(§3 — слой правил/NER, в который вырастает `slot_types.py`),

## 1. Зачем

Сейчас SWL (`intent_provider.py`) отдаёт `params` свободным объектом: что
GigaChat вытащил из фразы, то и уходит модулю. Модуль не знает заранее,
что ему придёт, и защищается от произвольного входа сам.

Пример: RVS распознал «посчитай двенадцать умножить на десять» как
«12 x 10», SWL передал строку как есть. Калькулятор
(`modules/calc/main.py`) разбирает выражение через `ast.parse` —
`12 x 10` это `SyntaxError`, модуль возвращает `{"status": "error"}`,
пользователь слышит «не смог посчитать». Чинить это в модуле — бесконечно
дополнять его знанием всех причуд STT. Логичнее: модуль объявляет, что
принимает на вход, а приведение к этому виду — не его забота.

Отсюда: **обязательная схема параметров у действия** — «шаблон команды».
Действие декларирует свои слоты (тип, обязательность, допустимые
значения), SWL приводит вытащенное из фразы к этой форме и проверяет,
прежде чем отправить.

## 2. Где это стоит

`params` — необязательный блок на **действии** (не на модуле), рядом с
`needs`/`produces`:

```json
{
  "command": "alarm_set",
  "needs": ["alarm_time", "alarm_label"],
  "produces": ["alarm_set_done"],
  "params": {
    "alarm_time":  {"type": "datetime", "required": true},
    "alarm_label": {"type": "text", "required": false, "default": "будильник"}
  }
}
```

`needs`/`produces` **не меняются** — плоские списки строк, слой графа для
GOAP-планировщика. `params` — отдельный слой (разбор фразы).
**Планировщик в `params` не заглядывает; SWL — только в `params`.** Тот
же принцип, что с `cost`: необязательное добавочное поле, одни части
системы его читают, другие игнорируют. Манифест остаётся слоёным, не
слитым.

Списки `needs` и `params` держим **раздельно** (решено — не объединять
`needs` в список объектов): сохраняет обратную совместимость (все 12
существующих манифестов валидны), не тащит топологию графа и NLU-разбор в
одну структуру, оставляет осмысленным случай «ключ в `needs`, но не в
`params`» (вход только от планировщика, из речи не берётся — напр.
`current_datetime` у `mod_journal`).

## 3. Граница ответственности: SWL нормализует форму, модуль разрешает смысл

SWL приводит значение к **представлению**, которое объявил слот. Он не
вычисляет и не разрешает ссылку на контекст.

| Делает SWL (форма) | Делает модуль (смысл) |
|---|---|
| «12 x 10» → «12 * 10» (переписал строку) | вычислил `= 120` |
| «двенадцать» → `12` | — |
| «семь утра» → `{hour: 7, minute: 0, meridiem: "am", date: null}` | «сейчас 8:30 → значит завтра» |
| «Питер» → «Санкт-Петербург» | нашёл погоду по городу |
| «заведи» → `alarm_action: "create"` | создал запись |
| charset/грамматика: `2 + + 3` не проходит | семантика: `10 / 0`, «будильника с таким id нет» |

Практическое следствие для `datetime`: SWL отдаёт **структуру полей**, а
не абсолютный момент. `date: null` — SWL не знает, сегодня или завтра, и
не должен. Перекат («время уже прошло → следующие сутки»), «завтра»,
«через час» — модуль; ему в параметрах приходит ещё и референсный
timestamp команды.

**Почему референсное время не идёт через SWL, а не только «не его дело».**
Три причины разом:
1. **Архитектурно** — SWL превращает фразу в структуру, ему неоткуда
   взять «сейчас» без внешнего состояния, а внешнего состояния у него
   нет и не должно быть (он статeless-трансформация фразы).
2. **Кэш промпта тир-2** (`local_brain_design.md` §3) — системный
   контекст держится статичным ради задержки; живое «сейчас» в каждом
   вызове было бы меняющимся префиксом, кэш не работал бы.
3. **Свежесть.** Между разбором SWL и фактическим запуском модуля
   проходит время (очередь `core/goals/`, планировщик). «Сейчас»,
   зашитое в момент разбора, к моменту исполнения устареет. Модуль
   берёт «сейчас» **в момент своего запуска** — оно всегда самое
   свежее из возможных.

**Разбор на примере `alarm_set`** (`alarm_time`: datetime, `alarm_action`:
enum create/edit/delete, `alarm_shift_seconds`: number) — три разных
способа фразе задать время, и во всех SWL не считает:

| Фраза | Что кладёт SWL | Кто и как разрешает |
|---|---|---|
| «на семь утра» | `alarm_time: {hour:7,...,meridiem:"am"}`, `alarm_shift_seconds: null` | абсолютное время, разрешать нечего |
| «перенеси на полчаса позже» (edit) | `alarm_time: null`, `alarm_shift_seconds: 1800` | модуль: точка отсчёта — время **существующего** будильника |
| «разбуди через 2 часа» (create, часа не названо) | `alarm_time: null`, `alarm_shift_seconds: 7200` | модуль: точка отсчёта — **момент выполнения** (`now()`), не время разбора SWL |

Одно и то же поле `alarm_shift_seconds` — точка отсчёта у него
**контекстная**: для `edit` это время существующей записи, для `create`
это момент запуска. SWL не различает эти два случая и не должен — он
просто увидел относительное смещение и вытащил его как есть.

## 4. Тип слота — контракт по проводу

`type` — единая точка правды для **обеих** сторон:

- **реестр типов в SWL** (`system/swl/slot_types.py`, новый файл): на
  каждый тип — пара `{validate(raw) -> bool, normalize(raw, ctx) -> value}`;
- тот же тип задаёт **форму значения**, которое уходит модулю в
  JSON-параметрах. Автор модуля смотрит `"type": "datetime"` — знает, что
  придёт `{hour, minute, meridiem, date}`, а не строка «7 утра» и не
  unix-время.

Стартовый набор типов:

| Тип | validate | normalize → форма |
|---|---|---|
| `text` | всегда | trim; строка |
| `integer` / `number` | числовое после нормализации | «двенадцать» → `12`; запятая → точка; число |
| `enum` | значение ∈ `values` | синонимы → канон (см. §5); строка из `values` |
| `datetime` | распознаётся как время | `{hour, minute, meridiem, date}` |
| `duration` | распознаётся | секунды (int) |
| `arithmetic_expression` | charset `0-9 + - * / ( ) . пробел` после нормализации | токен-aware: `x`/`х`/`×` между числами → `*`, `:` → `/`, «умножить на» → `*`; строка |
| `city` / `name` | — | позже, через NER (Natasha); нормализация форм («Питер» → «Санкт-Петербург») здесь же |

`normalize` — переписывание представления, без вычислений и без обращения
к «сейчас». `ctx` несёт то, что нужно для нормализации формы (напр.
язык); разрешение ссылки на контекст — уже в модуле.

## 5. enum-синонимы

Сопоставление «поставь / создай / заведи» → `create` — двумя слоями:

- **именованные типы** из общего реестра под частые случаи: `crud_action`
  (`create/edit/delete`), `toggle` (`on/off`) и т.п. — таблица синонимов
  в `slot_types.py`, манифест несёт только `"type": "crud_action"`;
- **`aliases` на слоте** — под доменные значения (`coffee_size`:
  «маленький/стандартный/большой»); если слот и с именованным типом, и с
  `aliases` — `aliases` дополняют/переопределяют таблицу типа.

Синонимы работают **только на шаге заполнения слота** — после того, как
модель намерения выбрала действие по смыслу всей фразы. В выборе цели
таблица не участвует: «создай» в произвольном предложении никуда не
«тянет», маршрут семантический. На bootstrap-этапе (GigaChat) таблицы
чаще не нужны — модель сама сопоставляет по списку `values`; окупаются на
офлайн-этапе, когда enum разбирает маленькое правило (линия 1.3).

## 6. Флаг `no_user_can_ask`

`catalog.py` сейчас кладёт в каталог целей **каждый** `produces`-ключ.
Часть ключей — промежуточные, нужные только планировщику для сцепки
(`city` от гипотетического `mod_location`, чтобы «погода» без города
находила город сама). Пользователь их голосом не просит, но модель
намерения видит их в списке и может выбрать на странную фразу.

Флаг `no_user_can_ask` на действии, **по умолчанию `false`**:

- `false` (по умолчанию) — действие и в графе планировщика, и в каталоге
  для модели намерения: пользователь может попросить его напрямую;
- `true` — действие только для планировщика: в каталог для SWL не
  попадает, найти его можно лишь поиском по графу как промежуточный шаг.

```json
{"command": "resolve_city", "produces": ["city"], "no_user_can_ask": true}
```

`catalog.build()` отдаёт SWL только действия с `no_user_can_ask != true`.
Планировщик по-прежнему видит все действия (ему `city` как внутренний узел
графа нужен). Чистые модули-ступеньки — редкость, поэтому помечаем
исключение, а не каждое нормальное действие.

## 7. `required` — только декларация

`"required": true` на слоте — пометка «этот вход обязателен». Что
происходит, когда SWL его не нашёл (ни из фразы, ни `default`, ни от
планировщика) — **за отдельной системой переспроса**, которая
проектируется независимо и здесь не описывается. До неё — существующий
путь: SWL не запускает действие, отдаёт исход «не хватает данных», CNPS
озвучивает. Поля для текста вопроса в схеме **нет** — это забота той
системы.

## 8. Что меняется в SWL

Три точки, все в существующих файлах:

1. **`catalog.py`** — запись каталога получает ещё и `params`-схему
   действия (и фильтруется по `no_user_can_ask`).
2. **`intent_provider.py`** — промпт «заполни форму»: перечисляет слоты
   выбираемых целей с типами, просит значения по слотам, «чего в фразе
   нет — не выдумывай». Ответ — по-прежнему `{goal, params}`.
3. **`swl.py`** — новый шаг `validate_and_normalize(goal, params)` между
   разбором и записью цели: по каждому слоту со схемой — `normalize` из
   `slot_types`, затем `validate`; невалидное — отбросить + лог. Дальше:
   обязательный слот пуст и есть в `needs` → оставить планировщику; есть
   `default` → подставить; иначе → путь ошибки (см. §7). Результат уходит
   в поле `state` файла цели (как сейчас).

## 9. Обратная совместимость

Действие без блока `params` → шаг 2 работает как сегодня (свободный
разбор), шаг 3 — no-op. Существующие манифесты не трогаются. `params`
добавляется модулю, когда ему нужен строгий разбор.

## 10. Как ложится на роадмэп

`slot_types.py` — тот самый шов, который в `local_brain_design.md` §3
становится офлайновым слоем: `enum`/`number`/`duration` → правила
(Yargy), `city`/`name` → NER (Natasha), `text` → как есть. Сделав схему +
типы с нормализаторами, написанными руками, начинаем работу 1.3 по
параметрам SWL — пока без дистилляции.

## 11. Что это даёт распознаванию — и что нет

Схема помогает не везде в пайплайне. По точкам отказа:

- **Мисхиринг STT** (акустика: «семь» → «восемь», «будильник» →
  «будни») — схема **не помогает никак**. Распознавание отдало не то
  слово — шаблон про это не знает.
- **Выбор цели** (какое действие) — помогает **косвенно**: чёткий
  каталог с типизированными слотами даёт модели намерения (и офлайновому
  классификатору) более ясный сигнал, на что похожа каждая цель. Эффект
  небольшой.
- **Извлечение значений слотов, их валидность и нормализация** — здесь
  **сильно**. «12 x 10» → «12 * 10», «семь утра» → структура полей,
  обрезка вежливых хвостов, проверка «значение по формату» до запуска
  модуля.

Переживает ли выигрыш переход на офлайн — **да, и там он больше**:

- На bootstrap GigaChat — большая общая модель, она и так неплохо
  вытаскивает «7 утра» и сама переписывает «12 x 10» из общих знаний.
  Схема тут страхует (зажимает вывод, ловит редкий промах), но модель
  выжила бы и без неё.
- Офлайн-стек — маленький классификатор намерения + правила/NER на
  слотах, у них **нет общих знаний**. Правило для
  `arithmetic_expression` работает только потому, что схема сказала «это
  арифметическое выражение, вот charset, вот карта операторов».
  Грамматика `datetime` срабатывает только потому, что слот типизирован.
  **Без схемы офлайн-экстрактору не на что опереться** — он не
  догадается, что «12 x 10» → «12 * 10». Здесь схема не удобство, а
  условие того, что офлайн-путь вообще работает без обвала качества.

Плюс схема **сужает задачу**: «выбери 1 из N целей и заполни
типизированный слот» — куда более узкая постановка, чем «разбери
предложение в произвольный JSON». Узкие задачи — ровно то, где маленькая
модель догоняет большую (тезис `local_brain_design.md` §2).

Честный предел: схема делает надёжной **сантехнику** (извлечение, формат,
нормализация). Она не улучшает «уши» (STT) и не делает умнее модель
намерения — если распознан мусор или выбрана не та цель, параметры не
спасут.

## 12. Открытые вопросы

- **`params` ⊆ `needs` или standalone-слот.** Слот, которого нет в
  `needs` (напр. `precision` у калькулятора, `alarm_label`) — планировщик
  о нём не знает. **Отложено:** решаем, когда появится реальный модуль с
  таким слотом, а не заранее.
- **`params` в манифесте vs `state` в файле цели.** Схема зовётся
  `params`, разрешённые значения едут в поле `state` файла цели
  (существующее). Возможно, стоит выровнять имена позже — не сейчас,
  трогает `core`.

Решено по ходу обсуждения: `description` на слоте — **не вводим** (тип +
имя слота достаточны для промпта). Имя флага — `no_user_can_ask`, по
умолчанию `false` (см. §6).

## 13. Реализовано (2026-09-10)

Bootstrap-версия, проверена офлайн (без живого GigaChat — разбор фразы
подменялся; вся нормализация/валидация детерминирована и покрыта).

**Новый файл `system/swl/slot_types.py`** — реестр типов, без
зависимостей (`re`, `ast`). `normalize(raw, slot, ctx=None)` → значение
нужной формы либо `SlotError`. Типы: `text`, `integer`, `number`, `enum`,
`crud_action`, `toggle`, `datetime` (→ `{hour, minute, meridiem, date}`,
`date` всегда `None`), `duration` (→ секунды), `arithmetic_expression`
(токен-aware: `x`/`х`/`×`→`*`, `:`→`/`, словесные операторы, одиночные
числительные словом → цифры, обрезка «посчитай…», charset + `ast.parse`),
`city`/`name` (лёгкая лексическая нормализация — настоящий NER в 1.3).
`_NAMED_ENUMS` — общие таблицы синонимов (`crud_action`, `toggle`);
слот-уровневые `aliases` их дополняют. `describe(slot)` — для промпта.
`python3 system/swl/slot_types.py` — таблица примеров.

**`system/core/module_init/manifest.py`** — структурная валидация
`no_user_can_ask` (bool) и `params` (объект; у каждого слота строковый
`type`; `required` bool; `values` непустой список и обязателен для
`enum`; `aliases` объект). Смысл `type` ядро НЕ проверяет — остаётся
независимым от SWL.

**`system/swl/catalog.py`** — пропускает действия с
`no_user_can_ask: true` (пропуск не помечает ключ в `seen`); в запись
каталога добавлен `params` (схема слотов действия, `{}` если блока нет).

**`system/swl/intent_provider.py`** — `SYSTEM_PROMPT` переписан на
«заполни форму»: слоты с типами/values, «значение бери как во фразе,
формат — задача системы».

**`system/swl/swl.py`** — новая `validate_and_normalize(goal, raw_params,
catalog_entry, trace_id)` между разбором и записью цели:
- слот со схемой → `slot_types.normalize`; `SlotError` → лог
  `slot_invalid`, слот отброшен;
- неизвестный `type` → лог `slot_type_unknown`, обработка как `text`;
- слот без схемы → пропуск как есть (обратная совместимость);
- обязательный слот пуст: `default` → подставить; иначе если в `needs`
  → оставить планировщику; иначе → лог `missing_required_param`, цель
  НЕ отправляется (озвученный переспрос — отдельная система, §7).
В `dataset.jsonl` пишется **сырой** разбор модели (обучающий сигнал);
нормализованные значения едут в `state` файла цели и в лог
`intent_extracted` (+ `raw_params` рядом).

**Манифесты:** `mod_calc.evaluate` → `params.expression:
arithmetic_expression (required)`; `mod_notes.add_note` →
`params.note_text: text (required)`; `weather.get_weather` →
`params.city: city (optional)`; `location.get_city` →
`no_user_can_ask: true` (демонстрация: `city` пропал из каталога целей,
но планировщик его по-прежнему достаёт для `weather`).

**Проверено сквозняком:** «посчитай двенадцать умножить на десять» →
