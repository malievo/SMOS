# Классификатор «команда / разговор» — схема совмещения: bootstrap → дистилляция → переключение

Статус: черновик для обсуждения, ничего из этого ещё не реализовано.
Описывает, как со временем перейти от временной модели-разметчика к
[обученному на эмбеддингах](embedding_classifier_design.md) локальному
классификатору, не требуя от конечного пользователя ручной разметки.

**Пересмотрено 2026-08-24** по итогам реального тестирования автором
проекта: изначальный вариант с ручной проверкой фраз пользователем (см.
историю ниже) годится только как **dev-инструмент для самого автора**
— обычный конечный пользователь не будет и не должен сам раскладывать
свои фразы по категориям. Также по тестам автора zero-shot ошибался
заметно чаще, чем хотелось бы, — в проде на bootstrap-этапе его
заменяет полноценная облачная LLM с constrained/structured output.

**Пересмотрено ещё раз 2026-08-24**: переключение с облачной LLM на
локальную модель — не одномоментное, а через промежуточный этап
проверки (см. шаг 3 ниже). В индустрии это называется **shadow
deployment** / **champion-challenger**: новая модель ("challenger")
какое-то время работает параллельно со старой ("champion") на реальном
трафике, её ответы только сравниваются и накапливаются, но не
используются для реальной работы системы — и повышается до основной,
только когда доказала, что справляется так же хорошо.

## Идея

Это по сути **дистилляция знаний** (knowledge distillation): сильная
модель-"учитель" (облачная LLM) размечает реальные фразы пользователя,
а на этой разметке обучается быстрая локальная модель-"ученик" —
классификатор на эмбеддингах. Как только "ученик" накопит достаточно
данных под конкретного пользователя, он проходит проверку в
shadow-режиме (шаг 3), и только после этого становится основным —
дальше обращения к облаку для классификации не нужны.

В любой момент ровно один классификатор **фактически используется** для
работы системы (либо облачная LLM, либо локальная модель) — второй,
если запущен, работает "в тени", только для сравнения и сбора данных.

Важно: локальная модель учится повторять суждения учителя (облачной
LLM), а не какую-то объективную истину. Расхождение между ними не
всегда значит, что локальная модель ошиблась — иногда это просто
пограничный случай самой фразы. Для дистилляции это нормально: смысл
именно в том, чтобы довериться учителю (см. решение про доверие LLM в
шаге 2 ниже).

**Стабильность системного промта.** Промт `ai_provider.py`
(`SYSTEM_PROMPT`) — это фактически определение "что такое команда, а
что разговор" для учителя. Пока идёт накопление датасета (шаги 2–3),
менять формулировку промта нельзя — иначе часть уже собранных примеров
окажется размечена под другое определение, и датасет станет внутренне
противоречивым. Если формулировку всё же нужно поменять — накопленные
до этого момента данные считаются устаревшими.

## Продакшен-путь (для конечного пользователя)

### 1. Первый запуск — online LLM как классификатор

Так как установка/настройка проекта в любом случае требует интернета,
первое время (bootstrap-период) каждая распознанная фраза отправляется
облачной LLM с системным промтом. Важно: ответ модели должен быть
**жёстко ограничен** через structured output / function calling API
(модель обязана вернуть строго `command` или `chat`, а не свободный
текст) — это снимает риск, что модель "не послушается" системного
промта, который есть у маленьких офлайн-LLM.

### 2. Параллельно — накопление датасета

Каждый ответ LLM (фраза + метка) пишется в отдельный рабочий
файл-датасет (не в общие логи — логи для истории событий, этот файл —
материал для обучения):

```json
{"text": "включи свет", "predicted_label": "command", "source": "llm_api"}
```

**Решение для MVP (2026-08-24):** не мудрить с уверенностью вообще —
LLM отдаёт только метку (`command`/`chat`), без самооценки уверенности
(пробовали добавить в промт — самооценка LLM всё равно не откалиброванная
метрика, решили не усложнять и убрали). Просто доверяем ответу LLM как
есть, без дополнительной проверки. Единичные ошибочные метки не должны
заметно повредить обучению маленького классификатора на сотнях примеров.
Возвращаться к вопросу фильтрации стоит только если на практике будет
видно, что локальная модель обучилась на реально плохих данных — тогда
разбираться предметно, а не защищаться от гипотетической проблемы
заранее.

### 3. Первое обучение → shadow-режим → циклы дообучения → переключение

**3a. Первое обучение.** Когда наберётся достаточно фраз конкретного
пользователя — важно именно **по каждому классу отдельно** (нужны и
примеры команд, и примеры разговора в достаточном количестве, не
просто общее число фраз, иначе модель хорошо выучит только тот класс,
которого было больше) — на них обучается локальный классификатор на
эмбеддингах (см. `embedding_classifier_design.md`). Порог N по каждому
классу не определён — подбирается на практике.

**3b. Shadow-режим.** Обученная модель не заменяет облачную LLM сразу,
а подключается параллельно. На каждую новую фразу отвечают обе:

- ответ облачной LLM (**champion**) идёт в дальнейшую обработку, как и
  раньше — пользователь ничего не замечает;
- ответ локальной модели (**challenger**) никуда не идёт, только
  сравнивается с ответом LLM.

Оба ответа (и когда совпали, и когда разошлись) добавляются в новый
набор данных для следующего раунда дообучения — расхождения особенно
ценны, но и совпадения тоже идут в сет.

**3c. Циклы дообучения.** Когда новый набор вырастет до нужного
размера — локальная модель переобучается на нём (промт-определение
учителя, см. выше, остаётся тем же, меняется только объём данных).
Цикл 3b→3c повторяется несколько раз, пока согласие между моделями не
станет высоким на большинстве новых фраз.

**3d. Переключение.** Когда согласие моделей стабильно высокое —
локальная модель становится основной (champion), облачная LLM
отключается от рабочего пути. В будущем здесь появится уведомление
пользователю о смене модели — сейчас не реализовано.

Открытый вопрос на будущее (сам автор это отметил): возможно, стоит
какое-то время после переключения продолжать держать облачную LLM в
shadow-режиме для наблюдения — обнаруживать, если локальная модель
начинает "плыть" (например, пользователь начал говорить по-новому).
Не решено, вернуться к этому позже.

## Dev-путь (инструмент автора, не для конечного пользователя)

Отдельно, для себя, автор уже реализовал и протестировал вариант с
ручной проверкой — полезно для подготовки собственных тестовых
датасетов или проверки качества модели, но это не часть пользовательского
пайплайна:

1. Классификатор (zero-shot или другой) размечает фразы автора.
2. Накопленные фразы (в первую очередь — с меткой `command`, так как
   ошибка там заметнее) складываются в отдельный файл.
3. При накоплении N фраз — автор вручную проходит по файлу и
   подтверждает/поправляет метки.
4. На проверенных данных обучается/тестируется модель.

## Открытые вопросы

- Пороги N по каждому классу — и для первого обучения (3a), и для
  размера набора на дообучение (3c) — подбираются на практике, не
  теоретически.
- Как именно измерять "согласие моделей стало высоким" (3c/3d) —
  нужен конкретный критерий (например, доля совпадений за последние M
  сравнений), сейчас это сформулировано только словами.
- Продолжать ли держать облачную LLM в shadow-режиме и после
  переключения (3d) — для наблюдения за дрейфом локальной модели со
  временем. Отмечено автором как идея на будущее, не решено.
- Уведомление пользователя о смене модели (3d) — не реализовано,
  запланировано на будущее.
- Стоимость bootstrap-периода и shadow-режима — каждая фраза, пока
  облачная LLM активна (как champion в 3b, так и после — если решим
  оставить её в shadow), это платный API-вызов; стоит продумать
  разумную длину обоих периодов.
