# CNPS — Centralized Notification/Playback System — дизайн

**Статус: v1 ПОСТРОЕН 2026-09-07 (на базе релиза v1.1.1), в дерево, не
закоммичен.** Стоит рядом с `system/core/`, `system/fwl/`, `system/swl/`,
`system/outputstructurizer/`, `system/sysaudio/`.

Код: `cnps.py` (демон: intake / conductor / control-UDP / housekeeping),
`classify.py` (класс важности по source + зажим), `synth.py` (движки
`gtts` женский / `piper` мужской тёплый `PiperVoice.load` / `spd-say`;
посентенсный кэш `.mp3`/`.wav`; цепочка запаса), `config.py`,
`log_client.py`. Конфиг — `user/configs/cnps.json`. Модуль-компаньон —
`system/modules/mod_playback/`. Правки соседей: `smos.py` (Proc audio →
cnps), `outputstructurizer` (пишет в `../cnps/tasks/`, `kind:"speech"`,
`source:"outputstructurizer"`, `voice:"gtts"`),
`core/task_runner._emit_completion` (флаг `silent`), `.gitignore`.

Проверено вживую (Piper + aplay): приём заявок, зажим класса
(`evil_module` + `class:CRITICAL` → AMBIENT), вытеснение ALERT→CHAT с
доигрыванием отложенного, pause/resume/skip/repeat, `kind:"clip"` через
sysaudio, отклонение битого JSON, TTL hard → NEVER, CRITICAL игнорирует
`stop`, пульс `mute.flag` (ставится на воспроизведении, снимается на
паузе/простое), `silent` гасит дублирующее подтверждение.

Первая попытка (сессия 2026-09-07, до отката) была построена, но не
закоммичена и потеряна; проект откатили до v1.1.1, дизайн и код
переписаны с нуля. Отличие от той попытки — раздел «Одна дорожка» ниже:
микшер уровня сэмплов из v1 **убран**, приглушение/наложение звука
отложено; `numpy` больше не нужен (вытеснение = `kill` проигрывателя).

CNPS **заменяет** `system/audio/` v1 в `smos.py` PROCESSES (не дополняет
его). `system/audio/` остаётся в дереве как история и как заглушка на
случай, если CNPS выключат в конфиге.

## Зачем отдельный процесс

**Динамик один.** Как только в системе больше одного источника звука —
ответ на команду, реплика watcher'а о поломке, будущий таймер, будущая
музыка — кто-то должен разрешать конкуренцию за устройство вывода:
что играет сейчас, что ждёт, что важнее, что выкинуть. Эта логика обязана
жить в одном месте. «Каждый компонент играет сам» разваливается на первом
совпадении и дублирует код воспроизведения везде. Это тот же принцип, что
у демона логов (`logs/listener`): системный процесс владеет ресурсом,
остальные шлют ему заявки fire-and-forget.

**CNPS — выходная сторона SMOS целиком.** FWL — вход (микрофон → текст →
классификация). `system/audio/` v1 умел только «сказать переданный текст».
CNPS — это тот «полный аудио-демон», который `system/audio/audio_design.md`
держал в планах: приоритет, вытеснение, время жизни заявок, повтор по
просьбе, синтез по частям — плюс синтез речи внутри самого процесса.

**По тесту «модуль vs системный процесс»** (см.
`system/swl/swl_design.md`) CNPS — однозначно системный процесс: работает
всегда, владеет ресурсом, в него прилетают заявки от многих источников.
Не модуль, не часть SWL-пайплайна, не живёт в `system/modules/`.

```
outputstructurizer ─┐
ядро / task_runner  ─┤
watcher (состояние) ─┼─► system/cnps/tasks/<id>.json ─► CNPS ─► колонки
sysaudio / инфра    ─┤        (заявка на воспроизведение)
любой компонент     ─┘
                              управление (стоп/повтори/продолжи/громче)
        mod_playback ───────► UDP :47120 ───────────────► CNPS
```

### Два канала входа — это не два режима

CNPS — один всегда работающий демон, и он слушает **оба** входа
одновременно. Разница не «общий / инженерный», а **очередь против
немедленного действия**:

| | Папка `tasks/` | UDP :47120 |
|---|---|---|
| Что несёт | *что воспроизвести* — речь, файл, клип | *действие над тем, что играет сейчас* — стоп, пауза, повтори, громче |
| Семантика | встать в очередь, дождаться приоритета | сработать сразу, мимо очереди |
| Кто шлёт | любой компонент (outputstructurizer, ядро, watcher, инфра) | `mod_playback` (по команде пользователя через ядро); v2 — стоп-споттер `wake.py`; CRITICAL-путь |
| Надо ли ждать | да, обрабатывается по порядку | нет, обрабатывается вне очереди |

`kind: "control"` можно положить и в `tasks/` — но это исключение
(отложенная команда «через минуту сделай тише»); всё срочное идёт по
UDP, потому что не должно стоять в очереди за синтезом. UDP — не
«внутренний» и не «привилегированный» канал: его штатный отправитель —
обычный модуль `mod_playback`, которым рулит голос пользователя.

## Что кладут на вход: манифест заявки

Отправитель шлёт **маленькую** заявку `system/cnps/tasks/<id>.json`
(атомарно, temp + rename; имя = `id`, уникальный и по времени → очередь
читается по порядку). Минимум полей — остальное достраивает CNPS.

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | уникальный, монотонный по времени; сквозная корреляция |
| `kind` | да | `speech` \| `file` \| `clip` \| `control` |
| `source` | да | кто прислал — **основной** сигнал важности (см. ниже) |
| `text` | для `speech` | что синтезировать и произнести |
| `wav_path` | для `file` | путь к готовому WAV; этап синтеза минуется |
| `clip_key` | для `clip` | ключ клипа `system/sysaudio/` (тоже без синтеза) |
| `class` | нет | *подсказка* желаемого класса важности; CNPS её зажимает |
| `ttl_soft_sec`, `ttl_hard_sec` | нет | подсказки; иначе — дефолты класса |
| `voice` (или `engine`) | нет | движок синтеза для `speech`: `gtts` \| `piper` \| `spd-say`. Нет поля — CNPS берёт по `source` (`synth.engine_by_source`), иначе общий дефолт |
| `intent`, `reply_to` | нет | корреляция с задачей ядра — для квитанций о доставке |

**Отправитель НЕ проставляет надёжно приоритет, TTL и флаги поведения.**
Он может *попросить* (`class`, `ttl_*`), но решает CNPS. Причина — в
следующем разделе.

`kind: "control"` в папке — альтернатива UDP-каналу для управления
(`{op: "stop"|"repeat"|"continue"|"pause"|"resume"|"louder"|"quieter",
target?: <id>}`); основной путь управления всё же UDP, потому что оно
должно бить мимо очереди.

## Аналитический слой: важность определяет CNPS, не заявка

Заявке нельзя доверять решение о важности. Иначе любой модуль (в т.ч.
кривой или написанный впопыхах) сможет прислать болтовню с максимальным
приоритетом и вытеснить реальное аварийное объявление.

**Надёжный сигнал — `source`, а не самозаявленный `class`.** У CNPS есть
таблица «источник → максимальный класс». Манифест может запросить класс,
но CNPS **зажимает его по потолку источника** (`min(запрошенный,
потолок)`; нет запроса — берётся дефолтный класс источника).

| `source` | Максимальный класс |
|---|---|
| `smos`, `updater`, инфраструктура | CRITICAL |
| `watcher` | ALERT (CRITICAL — только для железа/питания, отдельным флагом в конфиге) |
| `core` | ALERT |
| `outputstructurizer` | RESULT |
| `chat` (ветка друга) | CHAT |
| прочее / неизвестный source | AMBIENT |

**Кто вообще пишет в `tasks/` напрямую.** Ответы модулей пользователю
идут не напрямую, а через `outputstructurizer` — он и проставляет
`source: "outputstructurizer"`, то есть потолок RESULT. Прямой доступ к
`tasks/` — у `watcher`, ядра, инфраструктуры. Список «доверенных прямых
источников» — в конфиге; заявка с незнакомым `source` не отклоняется, а
получает AMBIENT (сыграет, если ничего важнее нет, и первой протухнет).

Порядок обработки одной заявки: `parse` → штамп `created_at` →
`resolve_class` (по таблице + зажим манифеста) → дефолты класса (TTL,
можно ли прервать голосом, доигрывать ли CRITICAL до конца) → в очередь →
арбитраж.

## Классы приоритета

Пять классов. Таблица параметров (пороги TTL, «прерывается ли голосом»,
«доигрывает ли до конца») — в `user/configs/cnps.json`, здесь — смысл.

| Класс | Кто типично шлёт | Пример | Вытесняет | Прерывается голосом |
|---|---|---|---|---|
| CRITICAL | инфраструктура, watcher (железо) | «запуск не удался», «нет места на диске» | всё | нет — доигрывает |
| ALERT | watcher (сеть/компонент), ядро | «пропал интернет», «модуль погоды не отвечает» | RESULT, CHAT, AMBIENT | да |
| RESULT | outputstructurizer | «сейчас 14:30», «записал» | CHAT, AMBIENT | да |
| CHAT | ветка chat | свободный разговор | AMBIENT | да |
| AMBIENT | фоновые модули | тихие подтверждения | — | да |

`privilege_level: 2`, которым `outputstructurizer` уже помечает свои
заявки (`outputstructurizer_design.md`), = RESULT. Совместимость: если в
заявке нет `class`, но есть `privilege_level`, CNPS маппит его на класс.

## Синтез по предложениям + кэш

CNPS синтезирует речь сам, **по предложениям**, не всей фразой сразу:

- **Быстрее первый звук.** Первое предложение произносится, пока
  синтезируются остальные. Для «сейчас 14:30» разницы нет, для длинного
  ответа — есть.
- **Чистые точки реза.** Прервать и потом продолжить можно на границе
  предложения, без обрыва на середине слова.
- **Дешёвый повтор и продолжение.** Каждое синтезированное предложение —
  файл в кэше по хешу `движок|голос|текст`
  (`system/cnps/cache/<hash>.{wav,mp3}`). «Повтори» и «продолжи» не
  пересинтезируют.

«Повтори» = играть заявку с первого предложения. «Продолжи» = с начала
**прерванного** предложения (то, что играло в момент прерывания, целиком
заново), не по-сэмвольно.

`kind: "file"` и `kind: "clip"` синтез минуют — играется готовый файл
(WAV или MP3, плеер по расширению).

### Два голоса: ассистент (gtts) и система (piper)

Различие «говорит ассистент / говорит инфраструктура» держится на
**разных движках**, а не на настройке одного:

| | Голос ассистента | Голос системы |
|---|---|---|
| Движок | **gtts** (Google TTS, женский, онлайн, MP3) | **piper** (`ru_RU-dmitri-medium`, мужской, офлайн, WAV) |
| Что озвучивает | ответы на команды, болталка — всё, что идёт через `outputstructurizer` | `smos`/`updater`/`watcher`/`core`: старт, ошибки, оповещения |
| Кэш | `cache/<hash>.mp3`, mp3-плеер | `cache/<hash>.wav`, wav-плеер (тёплый `PiperVoice`) |

**Как выбирается движок заявки:** поле `voice` в манифесте (если задано)
→ `synth.engine_by_source[source]` → `synth.engine` (общий дефолт).
`outputstructurizer` проставляет `voice: "gtts"` явно (ключ
`playback_voice` в его конфиге); плюс у CNPS в дефолтах
`engine_by_source["outputstructurizer"] = "gtts"` — подстраховка.

**Цепочка запаса** (`synth.fallback_engine`, по умолчанию
`["piper", "spd-say"]`): движок заявки не сработал (нет пакета / **нет
сети для gtts** / нет модели) → следующий по цепочке. То есть офлайн
ответы ассистента озвучит piper, потом spd-say, потом — печать текста.
Сбой синтеза никогда не роняет демон.

Это закрывает бывший открытый вопрос «голос ассистента vs системы»:
gtts и piper — заведомо разные на слух, оба уже в проекте (gtts —
прежний `audio.py`, piper — `sysaudio`).

## Одна дорожка: вклинивание и прерывание, без микшера

**В v1 — одна звуковая дорожка за раз.** Более важная заявка **прерывает**
текущую (останавливает воспроизведение, текущая уходит в «отложено», см.
TTL), синтезирует своё и играет. Никакого приглушения фоном, никакого
«звук поверх звука».

Автор осознанно отказался от микшера уровня сэмплов в v1: сценариев,
где нужно именно *приглушить* один звук под другой, пока нет —
приглушать нечего (музыкального модуля нет). Всё описанное поведение —
это «останови A, играй B», то есть приоритетная очередь с вытеснением, а
не микс.

**Механика.** Предложение играется отдельным процессом-плеером (`aplay`/
`paplay`, WAV из кэша). Прерывание = убить процесс-плеер текущего
предложения + снять с очереди остаток предложений этой заявки, записав
номер прерванного предложения. Возобновление = снова поставить в очередь
предложения начиная с прерванного.

**Поэтому v1 не нуждается ни в `numpy`, ни в звуковой библиотеке.** Синтез
пишет WAV, плеер их проигрывает по одному, вытеснение = `kill`. Кроссфейд
на стыке, плавное затухание при обрыве, реальное приглушение — всё это
завязано на свой микшер и относится к более поздней версии (см.
«Открытое»).

## Система времени жизни

Идея автора: **у каждой заявки — время жизни, и оно убирает право на
автоматическое воспроизведение, а не сам контент.**

Два порога (дефолты — по классу, заявка может подсказать):

- **`ttl_soft`** — «легко прервать». В пределах soft-порога заявку можно
  вытеснить и потом **сама** доиграет, когда очередь освободится.
- **`ttl_hard`** — «выбросить молча». После hard-порога заявка не играется
  и не продолжается **автоматически** вообще — ни новая, ни отложенная-
  недоигранная.

Что происходит с недоигранной заявкой:

1. Пришло что-то важнее → текущую прерываем, она уходит в **отложенные**
   с номером прерванного предложения.
2. Очередь освободилась, **soft-порог не прошёл** → отложенная сама
   доигрывает с прерванного предложения.
3. **Soft-порог прошёл** (пока лежала отложенной, или важное объявление
   было длинным) → отложенная **не** доигрывает сама. Уходит в буфер
   **Recap**.
4. **Hard-порог прошёл** → то же самое, плюс из очереди она тоже
   выкидывается молча, если ещё ни разу не звучала.

**Recap-буфер.** Хранит последние N произнесённых/недоигранных заявок
**независимо от TTL**. «Повтори последнее» / «что ты сказал» работает
после истечения любого порога — но только по явной просьбе пользователя,
сам CNPS протухшее не поднимает. «Повтори» из Recap = RESTART, «продолжи»
= с прерванного предложения (только если заявка была в отложенных).

**Чистка отложенных — в v1 только по времени.** Что снимать с
«отложенных» и когда, решают исключительно пороги TTL выше. Более точный
сигнал «пользователь сменил тему, брось отложенный ответ сейчас, не жди
таймера» — это `context_id`, но его сегодня негде взять (SWL/ядро
контекст реплики не ведут), и в v1.1.1 пользователь всё равно не может
задать новый вопрос, пока играет старый ответ — вход закрыт (см.
«Голосом во время воспроизведения» ниже). Отложено в «Открытое».

## Управление воспроизведением и модуль-компаньон

CNPS — **первый компонент SMOS, которым можно управлять голосом на ходу**
(«стоп», «повтори», «продолжи», «тише», «пауза»). И первый, у которого
есть **штатный модуль-компаньон** в `system/modules/`, задающий его
командный словарь. Это новое для проекта решение — осознанное.

**Разделение ответственности:**

- **CNPS** владеет механизмом: остановить, возобновить, сменить громкость,
  достать из Recap. Слушает управляющие команды на UDP :47120.
- **`mod_playback`** (`system/modules/mod_playback/`) — обычный модуль:
  манифест с `produces: playback.stop / playback.repeat /
  playback.continue / playback.louder / …`. Планировщик ядра вызывает его,
  когда SWL распознал соответствующую цель. Модуль переводит цель в
  UDP-фрейм для CNPS и **возвращает ядру `silent`** — чтобы
  `outputstructurizer` не проговорил ещё и текстовое подтверждение
  («останавливаю») поверх того, что только что оборвали.

**`silent` — правка в ядре.** `core/task_runner._emit_completion`: если
результат модуля содержит флаг `silent`/`_silent` — не писать файл-
результат в очередь `outputstructurizer`. Небольшая, но это изменение
ядра; фиксируется здесь как точка интеграции, делается вместе с CNPS.

**Три яруса управления** (от быстрого к общему):

1. **Стоп-слой в `wake`** — «стоп» / слово-отмена ловятся до
   классификатора и ядра, фрейм летит прямо в CNPS. Мгновенно. Сторона
   CNPS (приём фрейма) в дизайне есть; сторона `wake` (стоп-споттер во
   время озвучки) — **v2**, см. «Голосом во время воспроизведения» ниже.
2. **Плоский матчер в классификаторе** — «тише» / «громче» / «повтори» /
   «пауза» без активной сессии → `control` в CNPS мимо SWL/ядра, без LLM.
3. **Через ядро** — команды живой сессии, числа («громче на два»),
   неоднозначное: SWL → цель → `mod_playback` шлёт `control` сам.

Ярус-1 — v2. Ярусы 2–3 — по мере надобности; в первую версию достаточно
яруса 3 (`mod_playback` через ядро) плюс приём фреймов на UDP.

### Голосом во время воспроизведения — v2, стоп-споттер

С v1.1.1, пока SMOS говорит, `mute.flag` **закрывает микрофон** (`wake.py`
перестаёт слушать) — защита от петли «система слышит саму себя». Прямое
следствие: **пока CNPS играет, сказать голосом «стоп» / «отмена» нельзя**
— вход закрыт. Это конфликт двух решений.

**Решение автора (2026-09-07): barge-in — это v2, не v1.** v1 выходит
без голосового обрыва играющего; его закрывает вытеснение по приоритету
(ниже). v2 добавляет стоп-споттер.

**Что работает в v1 без микрофона:**

- **Вытеснение по приоритету.** watcher / CRITICAL шлют заявку файлом или
  по UDP — микрофон не нужен. Аварийное перебивает болтовню. Это основной
  способ «прервать играющее» в v1.
- **«повтори» / «продолжи» / «тише».** Произносятся *после* того, как
  воспроизведение кончилось или было вытеснено, — микрофон снова открыт.
  Recap-UX не страдает.
- Ярусы 2–3 в паузах между репликами.

**Что в v1 не работает:** оборвать голосом то, что играет прямо сейчас.
Ярус-1 стоп-слоя — v2.

#### План v2: стоп-споттер как второй режим `wake.py`

Ложится на то, что уже есть: `wake.py` — единственный владелец
микрофона, **уже на openWakeWord**, уже умеет `--nowake` (грузиться без
основной модели), уже читает `mute.flag`, и в его конфиге уже есть хук
под свою обученную модель (`wake_word.model_path`). Это не новая
подсистема, а второй режим `wake.py`.

**`mute.flag` не убирается — меняет смысл.** Сейчас: «оглохни целиком».
Становится: «режим воспроизведения» — полный цикл `wake → запись → STT`
на время озвучки по-прежнему выключен (иначе CNPS фразой вроде «…джарвис
уже поставил таймер…» разбудит сам себя — ровно та петля, ради которой
флаг и вводили), но **вместо** него крутится узкий стоп-споттер. То есть
v2 barge-in = «стоп» / «отмена» / «пауза» / «тише». «Перебить и сразу
задать новую команду» — ещё позже (нужна запись во время затухания CNPS
→ AEC или микро-мьют перед записью).

**Жизненный цикл:**

```
CNPS начал играть ──► пишет mute.flag (режим "playback")
  wake.py видит флаг ──► основную модель не грузит/не крутит,
                         вместо неё крутит стоп-модель(и)
  стоп-слово ──► UDP-фрейм прямо в CNPS (мимо классификатора/SWL/ядра)
             ──► CNPS рвёт текущее, чистит очередь
  очередь пуста ──► CNPS снимает флаг
  wake.py видит снятый флаг ──► выгружает стоп-модель, обычный цикл
```

**Самосрабатывание — главный риск, два слоя защиты:**

1. **На обучении.** Позитивы («стоп», «отмена», «хватит») генерит Piper —
   тот же, что синтезирует речь CNPS. Туда же **негативы голосом
   ассистента**: Piper наговаривает произвольные фразы, в т.ч. с
   «…остановка…», «…это не отмена…», модель учится на них молчать.
   openWakeWord так и тренируется (синтетика + корпус негативов).
2. **На исполнении.** CNPS знает, что и когда произносит: отдаёт `wake.py`
   свой output-таймлайн, а предложения, где стоп-слово встречается
   буквально, помечает — `wake.py` на это окно глушит детект. `mute.flag`
   теперь ведёт CNPS, координировать это — его работа.

С этими двумя слоями **AEC** (эхоподавление на входе: PulseAudio
`module-echo-cancel` / WebRTC) становится опциональным — для устойчивости
на высокой громкости, а не обязательным.

**Мелочи реализации.** Односложное «стоп» с глухим взрывным на конце —
слабый триггер (мало фонетики → ложные срабатывания); «отмена», «хватит»,
«стоп-стоп» надёжнее. Споттер шлёт **UDP-фрейм** (это ярус-1). CNPS
уважает `voice_interruptible` класса: «стоп» поверх CRITICAL
игнорируется/логируется, поверх RESULT/CHAT — рвёт. Задержка: чанки
openWakeWord ~80 мс + буфер `aplay` ~180 мс → обрыв за ~полсекунды.
Споттер живёт в `wake.py`/`rvs` (сторона микрофона), не в CNPS.

**Промежуточный вариант**, если barge-in понадобится раньше v2:
не-голосовой обрыв (горячая клавиша / кнопка) — надёжно, но для голосового
ассистента вынужденно.

**Почему это НЕ жёсткая загрузочная зависимость.** Автор сначала
предлагал: без `mod_playback` CNPS не поднимается вообще. От этого
отказались — это инверсия хрупкости: самая некритичная функция (голосовое
управление плеером) заблокировала бы самую критичную (аварийные
объявления). Если `mod_playback` сломан или отсутствует, CNPS **всё равно
стартует**: играет, вытесняет, ведёт TTL — просто управляющие фреймы
некому слать, и CNPS пишет об этом `WARNING` на старте. Зависимость при
этом никуда не девается, она *декларативная*: описана здесь, `smos.py`
поднимает оба, модуль стоит узлом в графе. «Первый компонент со штатным
модулем-компаньоном» — остаётся; просто компаньон нужен для управления, а
не для того, чтобы процесс ожил.

## Отношения с `system/sysaudio/`

CNPS `sysaudio` **не заменяет** — тот сознательно холодный, без
зависимостей, работает когда сломано всё (`sysaudio_design.md`). Две
связки, обе нужны:

- **CNPS играет клипы sysaudio** как `kind: "clip"` — верхняя приоритетная
  полоса (CRITICAL), без синтеза, готовый WAV из `system/sysaudio/clips/`.
  Один голос для инфраструктурных фраз, мгновенно.
- **`sysaudio` остаётся аварийным путём.** Пока CNPS не поднят (preflight,
  голосовой диалог апдейтера) или упал — `smos.py`/`updater.py` зовут
  `sysaudio.py <key>` напрямую, как сейчас. CNPS в этот момент не при
  делах.

## `flags/mute.flag` переезжает в CNPS

Глушение микрофона на время озвучки (анти-петля «система слышит саму
себя», v1.1.1) сейчас ставит `system/audio/audio.py`. Владельцем
становится CNPS, режим — «пульс»: пока CNPS что-то играет, он держит
`system/fwl/rvs/flags/mute.flag` в режиме `until` и продлевает его.
`system/audio/audio.py` свою постановку флага сохраняет — она просто не
работает, пока `audio.py` не в PROCESSES.

- **v1: контракт файла и `wake.py` не меняются** (см.
  `project_smos_mic_mute_flag`). Флаг = «`wake.py`, не слушай».
- **v2: контракт расширяется** — флаг = «режим воспроизведения»:
  `wake.py` не глохнет целиком, а переключается на стоп-споттер (см.
  «Голосом во время воспроизведения»). CNPS дополнительно отдаёт
  `wake.py` свой output-таймлайн для гейта против самоперехвата.

## Форма и файлы

```
system/cnps/
  cnps.py            демон: приём заявок, аналитический слой, арбитраж,
                     TTL, Recap, control-UDP, state.json, пульс mute.flag
  synth.py           синтез по предложениям + кэш WAV (Piper; spd-say запас)
  classify.py        resolve_class: source → потолок, зажим манифеста
  config.py          DEFAULTS + load(), общая схема user/configs/
  log_client.py      копия, MODULE_NAME = "cnps"
  tasks/             входящие заявки <id>.json (+ rejected/); в .gitignore
  cache/             синтезированные предложения <hash>.wav; в .gitignore
  state.json         что играет / очередь / отложенные / громкость; в .gitignore
```

**Треды внутри `cnps.py`:** приёмник (поллит `tasks/`), синтез-воркер,
плеер (гоняет очередь предложений через `aplay`), слушатель UDP-контроля,
housekeeping (TTL-переходы, пульс mute.flag, запись `state.json`). Общее
состояние под одним локом; управляющие фреймы обрабатываются вне очереди.

**`state.json`** читается без обращения к процессу — как везде в SMOS
(`core`, `audio`). Что сейчас играет, содержимое очереди, отложенные,
Recap (метаданные, не аудио), громкость.

**Конфиг** `user/configs/cnps.json`, общая схема (`DEFAULTS` +
`_deep_merge`, откат на дефолты при отсутствии/битом JSON). Набросок:

```python
DEFAULTS = {
    "enabled": True,                    # false -> заявки только в лог
    "check_interval_sec": 0.3,
    "players": [["aplay", "-q"], ["paplay"]],   # чем играть WAV
    "synth": {
        "engine": "piper",                      # общий дефолт движка
        "engine_by_source": {"outputstructurizer": "gtts"},  # ответы/болталка -> женский gtts
        "fallback_engine": ["piper", "spd-say"],             # цепочка запаса (gtts офлайн -> piper -> ...)
        "piper_voice": "ru_RU-dmitri-medium",
        "model_dir": "../sysaudio/models",       # переиспользуем модель sysaudio
        "piper_timeout_sec": 30,
        "gtts": {"lang": "ru", "tld": "com", "slow": False,
                 "players": [["gst-play-1.0", "--quiet"], ["mpg123", "-q"]]},   # mp3-плееры
        "spd_say_command": ["spd-say", "-w", "-l", "ru"],
    },
    "control_udp_port": 47120,
    "trusted_direct_sources": ["watcher", "core", "smos", "updater"],
    "source_ceiling": {                 # source -> максимальный класс
        "outputstructurizer": "RESULT",
        "watcher": "ALERT",
        "core": "ALERT",
        "chat": "CHAT",
    },
    "classes": {                        # пороги и права по классу
        "CRITICAL": {"ttl_soft_sec": 3600, "ttl_hard_sec": 86400, "voice_interruptible": False},
        "ALERT":    {"ttl_soft_sec": 300,  "ttl_hard_sec": 3600,  "voice_interruptible": True},
        "RESULT":   {"ttl_soft_sec": 60,   "ttl_hard_sec": 900,   "voice_interruptible": True},
        "CHAT":     {"ttl_soft_sec": 30,   "ttl_hard_sec": 300,   "voice_interruptible": True},
        "AMBIENT":  {"ttl_soft_sec": 15,   "ttl_hard_sec": 60,    "voice_interruptible": True},
    },
    "recap_size": 10,
    "mute_flag_path": "system/fwl/rvs/flags/mute.flag",
    "paths": {"tasks_dir": "tasks", "cache_dir": "cache"},
}
```

**Квитанции о доставке.** По завершении заявки CNPS пишет в шину логов
(и в `state.json`) исход: `DELIVERED` (проиграна целиком), `PARTIAL`
(прервана и не доиграна), `NEVER` (протухла, не звучала). С `intent`/
`reply_to`, если были, — чтобы отправитель мог сопоставить.

## Интеграции (делаются вместе с кодом)

- **`smos.py`:** `Proc("audio", …)` → `Proc("cnps", "system/cnps/cnps.py")`.
  Зависимостей сверх стандартной библиотеки у v1 нет (см. «Одна дорожка»);
  `piper` нужен для синтеза, но его отсутствие → откат на `spd-say`, не
  падение. `mod_playback` поднимать не надо — это модуль, ядро его
  подхватит сканом `system/modules/`.
- **`outputstructurizer`:** одна строка конфига — писать в
  `system/cnps/tasks/` вместо `system/audio/tasks/` (ключ
  `cnps_tasks_dir`, откат на `audio_tasks_dir`). `kind: "speech"`,
  проброс `intent` из записи задачи.
- **`core/task_runner._emit_completion`:** флаг `silent` в результате
  модуля → не писать в очередь `outputstructurizer`; проброс `intent`
  дальше.
- **`system/modules/mod_playback/`:** новый модуль (манифест + точка
  входа), переводит цели `playback.*` в UDP-фреймы CNPS, возвращает
  `silent`.
- **`.gitignore`:** `system/cnps/tasks/*`, `system/cnps/cache/*`,
  `system/cnps/state.json`.

## Что коммитится

Код (`cnps.py`, `synth.py`, `classify.py`, `config.py`, `log_client.py`),
этот док, `cnps_design_plain.md`, манифест `mod_playback`. Рантайм —
`tasks/`, `cache/`, `state.json` — в `.gitignore`. Модель Piper не
коммитится (переиспользуется кэш `system/sysaudio/models/`, уже в
`.gitignore`).

## Когда строить

Когда заглушки `system/audio/` v1 начнёт реально не хватать — первое
совпадение за динамик: таймер, который звонит поверх ответа на команду;
watcher, которому надо перебить болтовню сообщением о поломке; просьба
«повтори». До этого момента `audio.py` v1 закрывает «сказал ответ».

## Решено с автором (2026-09-07)

1. **Одна дорожка, вклинивание + прерывание, без микшера.** Приглушение
   звука отложено — нет сценариев и нечего приглушать. Отсюда: v1 без
   `numpy` и звуковых библиотек, вытеснение = `kill` плеера.
2. **Важность определяет CNPS по `source`, не по манифесту.** Таблица
   потолков; манифест зажимается. Вывод модулей идёт через
   `outputstructurizer` (потолок RESULT); прямой доступ к `tasks/` — у
   доверенного списка, чужой `source` → AMBIENT.
3. **`mod_playback` — модуль-компаньон, но НЕ жёсткая загрузочная
   зависимость.** CNPS стартует и без него (WARNING, управление
   выключено, воспроизведение работает). Зависимость декларативная:
   док + `smos.py` + граф.
4. **TTL убирает право на автовоспроизведение, не контент.** soft =
   «сама доиграет», hard = «молча выбросить». Истёкшее → Recap, только по
   просьбе. Отложенная в пределах soft — доигрывает сама. Recap хранит
   последние N независимо от TTL. Чистка отложенных в v1 — только по
   времени (TTL); `context_id` как точный сигнал сброса — в «Открытое»,
   первичен цикл SWL→ядро.
5. **Синтез по предложениям + кэш WAV по хешу.** «Повтори» = с начала,
   «продолжи» = с начала прерванного предложения. Ускоряет первый звук.
6. **Управление — UDP-канал мимо очереди; `silent`-флаг в
   `task_runner`** гасит дублирующее текстовое подтверждение. Ярусы
   wake / классификатор / ядро — по мере надобности, в v1 хватает
   яруса «через ядро».
7. **`sysaudio` — обе роли:** CNPS играет его клипы как верхнюю полосу
   (`kind: "clip"`), и `sysaudio` остаётся прямым аварийным путём, когда
   CNPS не поднят.
8. **v1 без голосового barge-in, обрыв играющего — v2** (решено автором
   2026-09-07: «сначала простой v1, прерывание в v2»). v1: вытеснение по
   приоритету (без микрофона), «повтори/продолжи» после окончания. v2:
   стоп-споттер как второй режим `wake.py` (openWakeWord — уже в стеке),
   `mute.flag` из «оглохни» становится «режим воспроизведения»,
   стоп-слово → UDP-фрейм в CNPS. Самосрабатывание закрывается обучением
   (позитивы + негативы голосом ассистента, оба от Piper) и гейтом по
   output-таймлайну CNPS; AEC — опционально.
9. **Два канала входа — не два режима.** CNPS всегда слушает и `tasks/`
   (что воспроизвести, в очередь), и UDP :47120 (действие над играющим,
   мимо очереди). UDP не «инженерный»/привилегированный — его штатный
   отправитель обычный модуль `mod_playback`.
10. **Два голоса по движку** (2026-09-07): `gtts` (женский, онлайн) —
    ответы и болталка, всё что идёт через `outputstructurizer`; `piper`
    (мужской, офлайн) — системные сообщения (`smos`/`updater`/`watcher`/
    `core`). Движок заявки: поле `voice` → `synth.engine_by_source` →
    дефолт. Запас: gtts офлайн → piper → spd-say → печать. Закрывает
    открытый вопрос про голоса. См. «Два голоса».
