# Системные данные экземпляра — дизайн

**Статус: идея по итогам обсуждения 2026-08-29. Кода нет, папка
`system/sysdata/` заведена под неё.** Это журнал решений, не
спецификация и не обещание. На момент записи проект на паузе после
закрытия сквозной петли (SMOS 1.0).

## Откуда идея

SMOS растёт, и всплыл вопрос: где системе хранить факты о самой себе —
когда её впервые запустили, какая сейчас версия проекта, сколько она
проработала. Первая формулировка была «отдельный демон, который
производит системные данные». По ходу разговора идея ужалась до
честного минимума (см. ниже раздел «Что реально нужно»).

## Ключевое решение: это не демон

Прогон через тест «системный процесс vs модуль» из
[`../swl/swl_design.md`](../swl/swl_design.md): системный процесс — тот,
кто работает всегда и **производит вход для остальной системы**, его
нельзя «опционально не вызвать» (микрофон, STT, классификатор, ядро,
демон логов). На системные данные никто не блокируется, они ничего не
стримят — это **пассивное хранилище факта**, а не процесс.

Форма, а не восьмой демон:

- **файл(ы)-запись** в `user/state/` (рантайм, вне кода — см. ниже);
- **тонкая библиотека** `system/sysdata/sysdata.py`: `read()` +
  хелперы записи + CLI (`python sysdata.py` печатает текущую запись —
  инспектируемость, как у остальных частей SMOS);
- **писатель — `smos.py`**. Лаунчер уже единственный, кто надёжно
  видит каждый старт и стоп (он и сейчас пишет
  `system/launcher/run/state.json` с `started_at` и pid'ами). Никакого
  ядра в этом пути — развилки нет, координировать нечего. Это тот
  случай «прямая связь там, где нет выбора».

## Данные живут вне кода

`user/` в `.gitignore` целиком (кроме `configs/`). Файлы экземпляра —
именно такой случай: их нельзя коммитить, и, что важнее, **будущая
система обновлений заменяет код в `system/`, но не трогает `user/`** —
значит запись «когда активирован» и уникальный id переживут обновление
только если лежат в `user/`. Поэтому `user/state/`, а `system/sysdata/`
держит только код и этот документ.

## Что реально нужно: два раздельных файла

Обсуждение сошлось на том, что данные разной природы и разной
востребованности не надо мешать в один файл.

### 1. `user/state/instance.json` — паспорт экземпляра

Идентичность конкретной установки. Маленький, почти неизменяемый.
Единственная часть с **подтверждённым применением уже сейчас** — база
для системы обновлений.

| Поле | Тип | Как заполняется |
|---|---|---|
| `project` | str | константа (`"SMOS"`). Файл самоописателен; если SMOS когда-нибудь форкнут/переименуют или несколько SMOS-подобных систем поделят инфраструктуру — файл говорит, что он такое. Стоит копейки. |
| `instance_id` | uuid4 | генерится один раз, **write-once**. «Какая это коробка» — для будущей телеметрии, регистрации, мультиустройства. |
| `activated_at` | ISO8601 | первый запуск, **write-once**. |
| `version` | str | из корневого файла `VERSION` (см. ниже), обновляется каждый старт. |
| `previous_version` | str \| null | ставится, когда `version` изменилась между запусками — **хук для апдейтера**. |
| `registration_key` | str \| null | **будущее.** Если у SMOS появится история регистрации/лицензирования — ключ ляжет сюда. Сейчас поля нет, только зарезервировано на бумаге. |

Пишет `smos.py` на старте, одна точка входа `ensure_instance_file()`:
создать, если нет; обновить `version`; выставить `previous_version` при
дельте. Стоп-хук не нужен — в паспорте ничего сессионного.

### 2. `user/state/runtime.json` — рантайм-данные

Сессии, суммарный аптайм, число запусков, платформа, детект падений,
(опционально) heartbeat с «последним признаком жизни».

**Статус: идея для идеи. Подтверждённого потребителя нет.** Автор прямо
сказал, что реального применения этим данным пока не видит. Форма
описана здесь, чтобы не растворилась, но строить — **только когда
появится настоящая нужда** (модуль аналитики; учёт частоты падений).
Когда/если дойдёт: `smos.py` получает start/stop-хуки, и это всё равно
библиотека + файл, а не демон.

Ориентировочные поля (не финал):

| Поле | Смысл |
|---|---|
| `schema_version` | версия формата самого файла (миграции читателя, отдельно от версии проекта) |
| `session_count` | инкремент на каждый старт |
| `current_session` | `{started_at, pid, clean_start}` — чистится на стопе |
| `last_session` | `{started_at, stopped_at, duration_sec, exit: clean\|crash\|unknown}` |
| `cumulative_uptime_sec` | бегущая сумма |
| `platform` | os/arch/python — каждый старт, ловит апгрейд окружения |
| `hostname` | каждый старт |
| `last_alive_at` | только если добавить heartbeat (см. ниже) |

«Текущее время» как хранимое поле не нужно — `datetime.now()` бесплатен
везде. То, что за ним стоит на самом деле («когда работало в последний
раз», «работает ли сейчас»), покрывают `last_session` / `current_session`.

Граница с `mod_sysinfo`: тот про «прямо сейчас» (CPU, RAM, диск, аптайм
ОС). `runtime.json` — про «между запусками SMOS». Не пересекаются.

## `VERSION` в корне репозитория

Источник истины по версии проекта — отдельный файл `VERSION` в корне,
одна строка (`1.0.0`), под гитом. Не в `smos.root` (тот — чистый
маркер корня, его грепают; мешать «я корень» и «я версия» не надо) и
не `__version__` в каком-то модуле (апдейтер-скрипт часто на shell —
плоский файл читать/писать тривиально, и он языконезависим).

Связка: апдейтер двигает `VERSION` → на следующем старте `sysdata`
видит, что `version` в `instance.json` отстала → пишет
`previous_version` → система обновлений знает, что нужно прогнать
миграции с такой-то версии.

## Кто читает

Честно: **сейчас — никто, кроме будущего апдейтера** (`version` /
`previous_version`).

- **Ближайшее реальное:** система обновлений (не построена).
- **Возможно:** тонкий `mod_sysdata` с `produces: ["instance_info"]`,
  зовущий ту же библиотеку — тогда голосовое «когда ты впервые
  запустился» идёт обычным GOAP-путём, как `mod_datetime`.
- **Спекулятивно:** модуль аналитики поверх `runtime.json`.

## Запись

- Атомарно (temp + `rename`), как всё читаемое на лету в SMOS —
  аналитика может читать параллельно.
- Ошибка в `sysdata` **не роняет `smos.py`**: try/except, лог
  fire-and-forget, дальше. Дисциплина как у `log_client`.
- Битый `instance.json` на чтении → в `instance.json.corrupt`, новый
  создаётся заново. В редком случае это теряет `instance_id` /
  `activated_at`. Для v1 — принять риск (потребителя всё равно почти
  нет). Если позже станет важно: продублировать эти два поля в
  отдельный `user/state/identity.json`, который пишется ровно один раз
  и больше никем не открывается на запись.

## Heartbeat — опционально и сильно позже

Единственная часть, которая хочет цикл: раз в N секунд обновлять
`last_alive_at`, чтобы после краха знать примерное время смерти
(`last_session.stopped_at ≈ last_alive_at`, `exit: "crash"`). Полезно
только учёту падений. Даже тогда — **не новый демон**, а фоновый поток
в `smos.py` или в `logs/listener` (он и так всегда жив). Начинать без
него.

## Открытые вопросы

- Нужен ли `runtime.json` вообще, или паспорт экземпляра + `VERSION` —
  это весь реально полезный объём. Пока перевешивает второе.
- `project` / `registration_key` — гадание на будущее; оставлены как
  заметка, не как требование.
- Формат `exit` в `last_session` (`clean|crash|unknown`) — если
  `runtime.json` когда-нибудь начнут делать.
